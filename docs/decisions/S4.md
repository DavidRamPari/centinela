# Session S4 decisions

## S4-01 — PostgreSQL alert sink: one transaction, one lock, folding in memory (2026-10-26, S4)

`createPgAlertSink` (`src/db/alert-sink.ts`) applies the in-memory sink's rules (S0-08) inside one transaction per `upsert` call: take a transaction-level advisory lock with a fixed key, load the open alerts (`new`/`acknowledged`) for the batch's dedup keys with `SELECT … FOR UPDATE`, fold or create in memory in candidate order, then write with one statement per kind of change (`INSERT … FROM jsonb_to_recordset` for new alerts, `UPDATE … FROM jsonb_to_recordset` for folded ones, `INSERT … FROM unnest … ON CONFLICT DO NOTHING` for event links). The single advisory lock serializes sinks across processes (the server and `npm run ingest` or `npm run demo` writing to one database) without per-key lock ordering and deadlocks; the row locks make a concurrent triage either wait for the fold or be seen by it (a just-closed alert is never folded into). A candidate folds into the open alert with the same dedup key that has the latest `last_seen`; in time-ordered input this is the in-memory sink's "latest alert" (a test runs the same candidates through both sinks and compares). Entity lists are capped at 100 values each, like event links: IPs and user names are attacker-chosen. Timestamps written by the sink are JavaScript ISO strings (millisecond precision, as the parsers produce), so every timestamp the API returns has millisecond precision.

## S4-02 — Pipeline defaults and persisted rule flags (2026-10-26, S4)

With a pool, `createPipeline()` now defaults to the PostgreSQL event store and alert sink; without one, alerts stay in the in-memory sink (orchestrator tests). Rule flags (S2's open point) live in a `RuleCatalog` (`src/pipeline/rule-catalog.ts`): `ready()` copies `rule_state` into the detection engine once (a failure, such as the database being down at start-up, is retried on the next call), `setEnabled()` writes `rule_state` then the engine. The orchestrator gained an optional `prepare` hook awaited before each run, and `createPipeline()` wires it to the catalog. When `createPipeline()` builds its own detector and has a pool it also builds a catalog, so `npm run ingest` honours disabled rules without S1's CLI changing. The server builds one detector and shares it between the pipeline and the rules API, so disabling a rule in the dashboard takes effect on the next batch. `AppDeps` gained `rules` (the catalog) and `hub` (the SSE hub), and `src/index.ts` wires them and warms the catalog up at start-up.

## S4-03 — Time ranges, cursors and filters (2026-10-26, S4)

- `to` defaults to now whenever it is absent, also when `from` is given (S3-03); `from` defaults to `to` minus 24 hours. A future `from` without `to` gives an empty range, not an error.
- Events are ordered by `(ts, id)`, alerts by `(last_seen, id)`, both newest first; the alerts time filter applies to `last_seen` (S3-07). Cursors are base64url of `ts|id` and are validated when decoded (ISO time, UUID): a cursor the server did not produce is a `400` with `errors[0].path = "cursor"`. Pages fetch `limit + 1` rows to know whether a next page exists, so a page that ends exactly at the last row has no cursor.
- `host` filters are case-insensitive (`lower(host) = lower($n)`); `user`, `action` and `ruleId` are exact. `ip` must be an IPv4 or IPv6 address (`400` otherwise) because it is compared with `inet` values; on alerts, `ip` and `user` match the entity lists (`jsonb ?`). `technique` matches the exact id (`techniques @> ARRAY[$n]`), so `T1110` does not return `T1110.001` alerts, as in the mocks.

## S4-04 — Full-text search uses prefix terms (2026-10-26, S4)

`q` on events uses the `events_message_fts` index (`to_tsvector('simple', message)`). The `simple` parser keeps tokens such as `sqlmap/1.8`, `nikto/2.5.0` and `/../../../etc/passwd` whole, so `plainto_tsquery('sqlmap')` finds nothing. The server therefore turns every whitespace-separated word into a quoted prefix term and ANDs them (`'sqlmap':* & 'union':*`): `sqlmap`, `nikto`, an IP address or `failed password` find what an analyst expects. Quoting makes every tsquery operator literal (quotes and backslashes are escaped), so no input can produce a syntax error; input with no lexemes (only punctuation) matches nothing. Substrings inside a token (`passwd` in `/../../etc/passwd`) are not found; that is the trade-off for an indexed search, and the dashboard's mocks (substring search) are more lenient.

## S4-05 — Triage transitions (2026-10-26, S4)

Allowed moves per target status (ARCHITECTURE §7, S3-09): `acknowledged` from `new`; `closed` from `new` or `acknowledged`; `new` from `closed` (reopen). Setting the current status again is allowed, so a note can be updated or a closed alert's resolution changed. Other moves (`acknowledged → new`, `closed → acknowledged`) answer `409` problem+json. The check and the update are one `UPDATE … WHERE status = ANY(allowed)` statement, so concurrent triage cannot race. The resolution is cleared whenever the status is not `closed`; `note: null` clears the note and an absent `note` keeps it. `POST /api/alerts/bulk` applies the same statement to all ids and returns how many alerts changed; unknown ids and disallowed moves are skipped, not errors. Every triage change is published on the live stream as `alert.updated`, so other open dashboards refresh.

## S4-06 — Rules list order and cursor (2026-10-26, S4)

Rules are listed by level (critical first), then title, then id. This order is total and independent of the filters, so the cursor is simply the base64url id of the last rule on the page and the next page continues after that rule's position: toggling `enabled` between pages never skips or repeats a rule. `q` is a case-insensitive substring of the title, name, description, id and path (as in the mocks). `matches` is the number of alerts the rule produced, over all time. With every vendored rule compiling (`docs/rules-report.md`), `supported=false` returns an empty list today.

## S4-07 — Statistics and the ATT&CK matrix (2026-10-26, S4)

Time series use `date_bin(bucket, ts, '1970-01-01Z')` and contain only non-empty buckets; the dashboard fills the gaps (S3-03). Top lists hold ten entries, ties broken by value; `topRules` counts alerts per rule and takes the title and level of the rule's most recent alert. The ATT&CK matrix follows the mocks (S3-07): per tactic in ATT&CK order, every parent technique sorted by name, each followed by its sub-techniques that have rules or alerts; `rules` counts supported, enabled rules and `alerts` counts alerts in the range (by `last_seen`), both by exact technique id. The ATT&CK data file is loaded once, on the first matrix request.

## S4-08 — Live stream limits (2026-10-26, S4)

The SSE hub (`src/realtime/hub.ts`) is the pipeline's publisher. It holds at most 50 streams; a further client gets `503` problem+json. It sends a `: ping` comment every 25 seconds (one timer, running only while clients are connected), writes `: connected` on open so proxies forward the headers at once, sets `X-Accel-Buffering: no` for nginx, and drops (destroys) a client whose unsent output exceeds 1 MiB instead of buffering for it. `data` is `JSON.stringify(alert)`, which escapes line breaks, so attacker-controlled text cannot add SSE lines (tested with hostile titles and notes). On SIGTERM the entry point closes every stream before the graceful shutdown, which would otherwise wait for its 10-second timeout.

## S4-09 — `npm run demo` (2026-10-26, S4)

`scripts/demo.ts` runs with `tsx` from the root `demo` script and imports the server's modules by relative path. It uses loggen's fixed seed (42) and three days of data, but the data ends at the current hour instead of loggen's fixed `2026-10-20` start: with fixed dates the dashboard's default "last 24 hours" (and soon every preset) would be empty. The data set is identical for runs within the same hour. It replays each generated file through one pipeline call, as `npm run ingest` does; correlation windows are per group and every group-by includes a host or an IP specific to one host, so file-by-file replay detects the same scenarios as one time-sorted stream (S2 tests the latter in memory). The demo refuses to load a second copy into a database that already holds events (`--reset` truncates `events`, `alerts` and `alert_events`, keeping `rule_state`), refuses `NODE_ENV=production`, prints per-file counts, alerts by level and the ground-truth check, and exits with code 1 when a scenario is missed. It does not write `samples/`; `npm run loggen` still does.

## S4-10 — `@centinela/loggen` is a devDependency of the server (2026-10-26, S4)

As S1 suggested, `packages/server` now declares `@centinela/loggen`, and the new end-to-end test imports it by package name. It is a devDependency: only tests and the demo use it, the production image installs the server's dependencies with `--omit=dev`, and no file under `packages/server/src` imports it. The code the demo and the test share (`src/pipeline/replay.ts`, `src/db/ground-truth.ts`) uses structural types for files and scenarios, so building the server never needs loggen's build output. S1's and S2's tests keep their relative imports (their files are theirs to change).

## S4-11 — End-to-end test (2026-10-26, S4)

`test/e2e/detection.test.ts` generates loggen's `--small` sample in memory, replays it through `createPipeline()` with the PostgreSQL store and sink and a rule catalog, and checks the stored alerts with `checkScenarios` (an expected rule must have an alert overlapping the scenario's time range that shares an IP or user with it, the S2 test's criterion, in SQL). It prints `detected 11/11 scenarios`. Background alerts are identified through the events they link: every line is stored verbatim as `message`, and the test asserts that line texts are unique before mapping them back to scenarios. The acceptance limit (at most two `high`/`critical` alerts from background traffic) is asserted as stated; the current count is 0.

## S4-12 — Web: no retries for client errors (2026-10-26, S4)

The web already used the real API unless `VITE_USE_MOCKS=true`, and every page has loading, empty and error states (S3). Against the real API one gap showed: TanStack Query retried every failed query three times with backoff, so an unknown alert id showed "Loading…" for about seven seconds before the error. `src/api/retry.ts` retries only network failures and `5xx` answers; `4xx` answers and responses that fail schema parsing show the error state at once. `src/app/query-client.ts` (S3's file) uses it as the default: a one-line change. Tests still set `retry: false`. The per-browser upload history (S3-09) stays: the API contract has no upload history endpoint.
