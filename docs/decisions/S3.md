# Session S3 decisions

## S3-01 — Design tokens are CSS variables with tested contrast (2026-10-26, S3)

`packages/web/src/index.css` defines every color as a hex CSS variable (`--c-*`) for the light theme (`:root`) and the dark theme (`.dark`), exposed to Tailwind through `@theme inline` as semantic utilities (`bg-surface`, `text-muted`, `border-line`, `bg-sev-high`, `text-sev-high-fg`, `bg-heat-3`…). Components never use raw palette colors, so both themes come from one place. `test/theme.test.ts` parses the file and checks WCAG AA (4.5:1) for every text/background pair in both themes, including the five severity badges and the five heatmap steps. Severity badges always carry an icon and a text label. Dark is the default; the choice is stored under `centinela.theme` (try/catch, like the language). To make the raw CSS import work in tests, `vitest.config.ts` enables CSS processing for `index.css` only.

## S3-02 — Code splitting (2026-10-26, S3)

Every page is a `React.lazy` chunk (`src/app/lazy-pages.ts`) rendered inside a `Suspense` in the layout. The ATT&CK data file is imported dynamically (`src/lib/attack.ts`) only by the views that show technique and tactic names, so it is a separate 127 kB chunk. The largest chunk is Recharts at 368 kB (budget 500 kB). The mocks are behind `import.meta.env.VITE_USE_MOCKS` and are tree-shaken out of production builds (verified: no fixture or MSW code in `dist/`).

## S3-03 — Time ranges: presets send only `from` (2026-10-26, S3)

The URL holds either a preset (`range=1h|24h|7d|30d`, default `24h` left implicit) or a custom range (`from`, optional `to`, ISO 8601). For presets the client sends only `from` (now minus the preset, floored to the minute so query keys stay stable) and relies on the server defaulting `to` to now. This keeps live refreshes correct: an alert that arrives after the page loaded is still inside the range when the list is refetched. **S4 must default `to` to now whenever it is absent**, also when `from` is given (the mocks do). Chart buckets: up to 3 h → `5m`, up to 3 days → `1h`, otherwise `1d`; the UI fills empty buckets with zeros, aligned to the Unix epoch like `date_bin`.

## S3-04 — Lists, filters and the URL (2026-10-26, S3)

Filters live in the URL (shareable views); invalid URL values are dropped, not reported (`readListParam`, zod parsing of techniques and ranges). Chips and selects apply immediately; free-text filters apply on submit, so typing does not send a request per key. Keyset pagination uses TanStack `useInfiniteQuery` with a "Load more" button; the cursor is not put in the URL (a cursor without the pages before it is not a useful shared view). The event drawer is in the URL (`/events?event=<id>`) so the alert timeline can link to one event. Tables use a roving tab stop: one row is tabbable, arrow keys/Home/End move, Enter opens; the drawer is a modal dialog that traps Tab, closes on Escape and returns focus to the row.

## S3-05 — Live updates (2026-10-26, S3)

Following ARCHITECTURE §10, the SSE `data` of `alert.created` / `alert.updated` is the `Alert` itself (the event name carries the type), parsed with `alertSchema`; malformed messages are ignored. The UI talks to a small `LiveSource` interface (`src/features/live/live-source.ts`): the browser implementation wraps `EventSource('/api/stream')`, closes it on error and reconnects with its own backoff (1 s doubling to 30 s); after a reconnect the alert views are refetched. Every change invalidates alerts, stats, ATT&CK and rules queries; `alert.created` also raises a toast linking to the alert. With `VITE_USE_MOCKS=true`, a fake source adds a new alert to the mock database every 45 seconds; tests drive a fake source by hand. Without `EventSource` (jsdom) the source is a no-op.

## S3-06 — Mock data (2026-10-26, S3)

`src/mocks/fixtures/build.ts` builds a deterministic database from a seed (own mulberry32 PRNG and UUIDv7 generator, never `Math.random`) with timestamps relative to `now`, so the default "last 24 hours" is always populated: 322 events over all four sources (271 in the last 24 hours) (background traffic plus the §4.3 scenarios, a Windows workstation and an Apache intranet host for variety) and 35 alerts over every level, status, rule type and 26 techniques, including hostile strings (`<script>`, `<img onerror>`, `' OR 1=1--`) and an event cut at 8,192 characters. Rules: the 12 Centinela rules of §6.1 (mock ids; S2 writes the real files) and 47 vendored SigmaHQ rules whose metadata was extracted once from `rules/sigma/` into `sigma-rules.ts`; their YAML source is imported raw with `import.meta.glob` (mock chunk only), and a test checks the extracted metadata still matches the files. The unsupported and disabled flags on two and one SigmaHQ rules are illustrative, to exercise the UI; S2's engine decides real support.

## S3-07 — Mock handlers mirror the API contract (2026-10-26, S3)

Handlers validate query strings, path parameters and bodies with the shared schemas and answer `400` problem+json like the server, so the UI cannot depend on lenient mocks. Semantics the UI expects from S4, as implemented in `src/mocks/queries.ts`: newest first by `(ts, id)` (alerts by `lastSeen`); the alerts time filter uses `lastSeen`; `technique` filters match the exact id; `host` is case-insensitive; `ip`/`user` on alerts match the entities; `q` is a case-insensitive substring in the mocks (FTS on the server). `GET /api/attack` returns, per tactic, every parent technique sorted by name followed by its sub-techniques that have rules or alerts; counts use the exact technique id. The UI renders whatever list the server returns (sub-techniques are indented by their dotted id), so S4 may choose a different selection. The upload mock counts lines that look like the chosen source.

## S3-08 — ATT&CK cell links depend on the view (2026-10-26, S3)

In the default "Alerts" view a cell links to `/alerts?technique=<id>` and keeps the matrix's time range; in the "Rule coverage" view it links to `/rules?technique=<id>`, which is what an analyst looking at coverage wants. Counts are always printed in the cell and the legend explains the scale in text, so the heatmap does not rely on color.

## S3-09 — Triage and ingest details (2026-10-26, S3)

Triage allows `new → acknowledged`, closing from `new` or `acknowledged` (a resolution is required and chosen explicitly), and `closed → new` (reopen, resolution cleared); the note is sent with each action. The ingest form validates source, host and time zone with the shared `ingestQuerySchema` and the 5 MB limit before reading the file. The "last uploads" list is a per-browser convenience in localStorage (`centinela.uploads`, at most 10 entries, re-validated with zod on read); S4 or S6 may replace it with server-side history. The `curl` example uses the page origin and `$INGEST_TOKEN`, never a real token.

## S3-10 — Placement and dependencies (2026-10-26, S3)

Page components live in `src/pages/`, their parts in `src/features/<area>/`, shared UI in `src/components/ui/`. The empty Playbook panel is `src/features/alerts/playbook/PlaybookPanel.tsx`, inside the folder S7 owns, so S7 only replaces that file. No dependency was added. Recharts' own bundle contains the string `dangerouslySetInnerHTML` (library internals); Centinela's code never uses it, and `test/lint-ban.test.ts` proves the repository ESLint config rejects both forms.
