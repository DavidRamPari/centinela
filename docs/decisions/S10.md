# Session S10 decisions

S10 opens the work from version 0.1 to 1.0. David asked for a plan, by phase, to turn Centinela from a small SIEM into one an organization can run every day, and approved it before this session. S10 writes that plan and the contracts of its first phase into the repository and changes no code. It touches the READMEs for three lines each (the roadmap, the contribution guide, the notice file) and leaves the PLAN status table to David, who adds S9 and S10 to S17 when he merges.

## S10-01 — The roadmap is `docs/ROADMAP.md`; `docs/PLAN.md` holds only the phase in progress (2026-11-14, S10)

`docs/PLAN.md` is what a session reads to do its work, so it has to be exact: paths, build list, acceptance criteria. Writing 39 sessions to that level now would produce a document that is stale before most of them run, because what real users ask for will reorder phases 3 and 4. The roadmap lists every phase with its goal, its sessions in one line each, what closes it and what stays out; PLAN gets the full specification of a phase when that phase opens, written by its first session together with the contracts (S10 for phase 1, S18 for phase 2, and so on). The roadmap carries no dates: they depend on the pilot more than on the code. Conversations with users and everything about the business are tracked outside the repository.

## S10-02 — Phase contracts live in `docs/ARCHITECTURE.md` §16 and empty as they are built (2026-11-14, S10)

`CLAUDE.md` tells every session that ARCHITECTURE is the contract, so the contracts of phase 1 go there and not in a separate file a session might not read. §16 is marked as planned in its first line, so nobody takes it for a description of version 0.1. The session that builds a part moves it into the section it belongs to and deletes it from §16; when phase 1 closes, §16 is empty and the next contract session replaces it. A session may correct the contract when building proves a detail wrong, with the reason in its decision file.

## S10-03 — Live detection orders events with one horizon on detection time (2026-11-14, S10)

With several machines sending at once, three things depend on the order in which events are evaluated: which events a correlation fires on, whether its window was already cleared by an earlier firing, and whether a match folds into an open alert or starts a new one (the 15 minutes of §7). Version 0.1 never met the problem because it evaluates one file at a time. Three designs were weighed:

- **Evaluate on arrival and rely on the 60 seconds each group already tolerates.** Nothing to build, but the result depends on arrival order in ways no test can pin down, which gives up the property the engine is built on (D-003).
- **A watermark per stream, releasing up to the minimum over active streams.** Handles a host whose clock is behind, but a quiet stream holds the minimum back, so every stream needs a liveness rule on the wall clock and the state grows with the number of hosts.
- **One horizon: the newest detection time seen minus a window (chosen).** One number, one sorted buffer. Events leave it in order, so a run without late events is exactly the reference run, and late events are counted, so a run always knows whether it was exact. The cost is that a host whose clock is behind by more than the window is always late; the hosts page (S14) shows that lag.

Two details follow from the choice. The wall clock appears in one place, the idle release, and only decides when to stop waiting; the engine still never reads it. And `ack=evaluated` stays the default so that scripts, uploads and every existing test keep final alert counts in the answer, while shippers ask for `ack=stored` and do not wait for the horizon.

For restarts, the checkpoint is exact after a clean shutdown and at least once after a crash. Exactly once would need the checkpoint written in the alert sink's transaction for every batch that changes an alert; correlation state is bounded but attacker-influenced (100,000 groups per rule), so that write could reach megabytes several times a second during a storm. S12 measures it and may tighten the guarantee.

## S10-04 — A timestamp from the future blinds correlation in version 0.1 (2026-11-14, S10)

Found while writing the ordering contract and reproduced against the engine at commit `5da97e3`, with the rules in `rules/` and SSH sign-in failures on `bastion-01`:

- **The same group.** Three failures from `203.0.113.45` at 11:00:00 to 11:00:02, one more from that address dated `2030-01-01T00:00:00Z`, then twelve more at 11:00:03 to 11:00:14. Without the event from 2030 the brute-force correlation fires; with it, nothing fires. The group's newest time is now in 2030, so every real match is more than 60 seconds late and `CorrelationState.add` ignores it.
- **Every group.** One failure from another address, `198.51.100.7`, dated 2030, then thirty failures from `203.0.113.45`, each in its own ingest call (process, then `flush` at the call's newest event time, as the orchestrator does). Without the event from 2030 the correlation fires three times; with it, never. The engine's watermark is now in 2030, `flush` sweeps with it, and every group whose newest match plus timespan is before 2030 is evicted at the end of every call.

So one event dated far ahead, from any host, stops every correlation whose matches arrive in more than one request, until event time passes that date or the server restarts. Rules that match a single event are not affected. It needs an event the parsers accept: RFC 3339 syslog lines, web access logs and Sysmon events carry a full date; RFC 3164 lines are held to 24 hours ahead of the receive time. A machine with a wrong clock is enough, and so is anyone with an ingest token.

S10 changes no code, and the fix belongs to the contract S12 builds (ARCHITECTURE §16.4): the detector receives the detection time, `min(ts, receivedAt)`, and an event more than `MAX_FUTURE_SKEW_SECONDS` ahead is rejected. Both reproductions become regression tests there. Until then the gap is stated in `docs/DETECTION.md`, in the residual risks of `docs/THREAT_MODEL.md` and in the READMEs. S16 (syslog over UDP, where a sender chooses its timestamp and can forge its address) depends on S12 for this reason.

## S10-05 — `tenant_id` arrives with the first table of phase 1 (2026-11-14, S10)

Several organizations in one installation is phase 5, but the column that separates their data costs almost nothing on a table that is being created and a migration plus a review of every query on a table that already holds data. Every table created from S12 on carries `tenant_id` with a default organization; S19 adds it to today's tables when it rebuilds `events` for partitioning. Until S38 it is only a column. ARCHITECTURE §16.1 says so in as many words, because a half-built boundary that looks finished is worse than none.

## S10-06 — No agent of Centinela's own; Fluent Bit with a generated configuration (2026-11-14, S10)

An agent is a privileged program on every machine of a customer that someone has to sign, update and answer for. Fluent Bit is open source, reads Linux files, journald and the Windows event log, and its HTTP output does what ingest v2 needs. Checked in its documentation on 2026-11-14: the output sends `json_lines` (NDJSON) among other formats, compresses with gzip, takes custom headers (the bearer token) and, from version 5.2, treats `429` and `503` with `Retry-After` as a signal to wait; the Windows event log input reads named channels and can deliver `EventData` as a named map. One request stays one source and one host, so the generated file has one output per input and the server needs no envelope format: Fluent Bit's tail input can name its key `message`, which is the key the NDJSON decoder already reads for line sources. The exact shape of its Windows records is taken from real captures in S14, not from memory.

## S10-07 — A token's scope covers what the events say, and limits are per token (2026-11-14, S10)

Checking only the request's `source` and `host` would leave the gap open: a syslog line names its own host, and a token for `web-01` could still write events that claim to come from `db-01`. The scope is therefore checked again on each parsed event. Host patterns are exact names or a prefix ending in `*`, compared in code; a pattern typed by a user is never compiled as a regex. Rate limits move from the client address to the token, because many hosts of one office share an address; requests without a valid token stay limited per address, which is what slows guessing.

## S10-08 — Monitors raise `system` alerts and run on the wall clock (2026-11-14, S10)

"This host stopped sending" cannot be decided on event time: the missing events are the signal. Putting it inside the detection engine would break the rule that the engine never reads the clock. It is a monitor of Centinela's own inputs, outside the engine and outside the determinism guarantee, with a third rule type so the alert pages, the API and the sink treat its alerts like any other. Absence expressed as a correlation over events (a backup job that did not log) is a different thing and stays on event time; it is S24.

## S10-09 — `LICENSE` holds the MIT text only; third-party terms move to `NOTICE` (2026-11-14, S10)

GitHub showed the repository without a recognized license: the paragraph about the vendored rules at the end of `LICENSE` kept its detector from matching the MIT text. `LICENSE` is now that text and nothing else. The paragraph moved to `NOTICE`, which also lists the ATT&CK data and the fonts with the terms the README already credited. The READMEs point to it. `CONTRIBUTING.md` is new: what helps, how to set up, the bar a change has to meet, the rule about never editing `rules/sigma/` and sending fixes to SigmaHQ instead, sanitizing sample logs, and reporting vulnerabilities in private. Contributions are accepted under the project's own license.
