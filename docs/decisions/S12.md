# Session S12 decisions

S12 builds live detection: the part of the phase 1 contract that was ARCHITECTURE §16.1 and §16.3 to §16.5 and is now §6.2, §6.3 and §8.1. Events from several machines are evaluated in the order they happened, a timestamp from the future can no longer blind correlation (S10-04), and a restart keeps the open windows. Files touched outside the paths the session owns are listed in S12-08.

## S12-01 — What D-003 means from now on (2026-11-14, S12)

D-003 said: rules are evaluated in memory, correlation windows use event time, the same input gives the same alerts. Three parts of it change meaning.

- **Event time becomes detection time.** The engine still never reads a clock, but the time it is given is `min(ts, receivedAt)`, not `ts` alone. The wall clock therefore enters the result in exactly one way: as the moment an event was received, which bounds its time from above. It also decides two things that never change what an alert contains: when the pipeline stops waiting for slower machines (the idle release) and when the state is saved.
- **"The same input" is a set of events, not a sequence.** The reference is the run that evaluates the set in order-key order (ARCHITECTURE §6.2). A live run in which no event is late and none leaves the buffer early gives exactly those alerts; a run with late or early events counts them, so it can always be told whether it was exact. Replaying files one after another, as `npm run demo` and `npm run ingest` do, is by this definition a run with late events, evaluated file by file as in version 0.1.
- **State in one process, but not lost with it.** Correlation windows and the reorder buffer are still held by one process, and several evaluating processes stay out of scope until phase 6. A restart no longer clears them (S12-05).

## S12-02 — Detection time, and what happens to a timestamp from the future (2026-11-14, S12)

An event dated ahead of the moment it is received is evaluated at the receive time; one dated more than `MAX_FUTURE_SKEW_SECONDS` ahead (a day by default) is rejected with `timestamp too far in the future`, and one whose time is not a date is rejected with `invalid timestamp`.

- **Clamp, not reject, inside the bound.** A machine set to the wrong time zone is up to fourteen hours ahead and its events are real. Rejecting them would lose evidence because of a configuration mistake; clamping keeps the event and takes away its power over the detector's clock.
- **Reject beyond it.** A day ahead is a broken clock or an attack. Stored, such an event would sit at the top of every list ordered by time until its date arrived.
- **The stored `ts` is never changed.** It is what the log line said, and the event list shows it. An alert raised from a clamped event shows the detection time as first and last seen, because that is the time the correlation counted with.

Both sequences reproduced in S10-04 are regression tests, together with their "minutes ahead" variants (`test/pipeline/future-timestamps.test.ts`). The variants send one failure per request with `ack=stored`, as a shipper does: with `ack=evaluated` and a fixed receive time the test itself would make every event late and prove nothing.

## S12-03 — Order key, the buffer and the two acknowledgements (2026-11-14, S12)

The order key is `(detection time, host, source, id)`, compared as code units so that every machine sorts it the same way. Ids are UUIDv7 assigned in line order, so one stream's events keep the order they were written in when their times are equal. The buffer is a binary heap; it never reads a clock, and its owner decides idle release and draining.

`ack=evaluated` releases everything up to the call's newest event, including older events of other streams, and then answers: the alert counts in the answer are final, which is what the upload page, the command line and every test written before S12 expect. `ack=stored` answers once the events are stored and reports how many still wait. Several machines sending with `ack=evaluated` at the same moment make each other's events late, because every call moves the last released key forward; machines that send as things happen use `stored`.

The upload route and the command line take no `ack`. `packages/shared` exports `uploadQuerySchema` for them, so the request the dashboard sends is the same as before this session.

## S12-04 — Streams, and why `events.stream_id` has no foreign key (2026-11-14, S12)

A stream is one delivery path: `(organization, kind, token, source, host)`. Its counters are updated once per ingest call, not per event. `host` is a query parameter, so the holder of a token chooses how many rows it creates; a token is refused a new stream once it has 1,000 (403).

- `token_id` is null in every row until S11 passes the id of the token that authenticated the request. Until then the variable token and all stored tokens share one bound of 1,000 streams.
- `events.stream_id` is a plain column, without a foreign key or an index. The events table is the insert path that bounds throughput, S18 will partition it, and nothing reads events by stream yet; the session that adds such a query adds the index it needs.
- `tenants` has one row and every table created from migration 004 on carries `tenant_id` with that row as default. It is a column, not a security boundary: nothing filters by it yet (phase 5).

## S12-05 — The checkpoint is exact after a clean stop and at least once after a crash (2026-11-14, S12)

S10-03 left open whether S12 could give exactly once. It cannot at a reasonable cost, and the measurements say why. Exactly once needs the saved state to commit in the same transaction as every alert it produced. On the development machine a snapshot of 200 open groups is 0.16 MB of JSON and takes about 3 ms, but a scan from 50,000 addresses that leaves 100,000 groups open is 80 MB of JSON (2.3 MB compressed), about 1.1 s to save and 2.3 s to restore. An attacker chooses how many groups are open, so a write per alert would let a scan stall ingestion.

So the state is saved on a clean shutdown and every `DETECTOR_CHECKPOINT_SECONDS` (15) while something changed:

- **Position.** The checkpoint records the id of the last event handed to the buffer. At start the server restores the windows, reads the buffered events back by id, then reads every event stored after the position, in id order, and evaluates them again.
- **After a crash** those events may have been evaluated once already. A firing that repeats folds into the alert it raised the first time (same dedup key, inside the 15 minutes of §7), so no alert is lost and none is doubled, but its `count` can be higher by the matches of that stretch. The acceptance test checks exactly this on three seeds.
- **The command line's events are not replayed.** `npm run ingest` and `npm run demo` evaluate what they store in their own process; a server that read them back would evaluate them a second time. The reader skips streams of kind `cli`, and events without a stream (stored before migration 004).
- **A first start evaluates nothing.** With no checkpoint the server marks the newest stored event as its position: history that was ingested before stays as it is.
- **A rule that changed loses its own windows.** State is keyed by rule id and a fingerprint of the correlation block (type, rules, `group-by`, timespan, thresholds, field).
- **The saved state is input.** It is validated with zod before use; one that fails, or carries another version, is ignored, the detector starts clean and the position is kept.

Known limits: a state too large to serialize is not saved (the failure is logged and the previous checkpoint stays); building the snapshot of 100,000 groups holds the event loop for about half a second; the server wiring in `index.ts` (restore at start, the timer, the save before the pool closes) has no automated test and was checked by hand against PostgreSQL, with `SIGTERM` and with `kill -9`.

## S12-06 — The demo data cannot tell an ordered pipeline from an unordered one (2026-11-14, S12)

The acceptance test delivers the demo data in seeded shuffles and compares every alert with the reference run. While building it I ran the same comparison with the buffer disabled (a window of zero, 1,843 late events) and with the files replayed one after another (8,456 late events): the alerts were identical to the reference in both. The scenarios of the demo happen on one host each, minutes apart, so no alert depends on how two streams interleave.

A test that passes without the code it tests proves little, so `future-timestamps.test.ts` has a case built to depend on order: one address sprays passwords at two hosts, ten user names on one and five on the other in between. In order, the alert fires at 4.5 s with five events from each host; evaluated on arrival, it fires at 9 s on one host's events alone. The test checks the first for both delivery orders, and the second when the window is zero. The loggen scenarios should gain an attack across hosts when a session next touches them.

## S12-07 — A window stays open one timespan after its last match was evaluated (2026-11-14, S12)

Found while writing the known gaps. Version 0.1 evicted a group when the watermark passed its newest match plus the timespan. For a machine that is late for good (a clock twenty minutes behind, or a backlog sent after an outage) that moment has passed before the event arrives, so its windows were evicted at the end of every request: ten failed sign-ins sent one per request never added up, with any clock more than a timespan behind. It is the mirror of S10-04, limited to the late machine's own groups, and a machine with a slow clock is more common than one with a clock in 2030.

A group now records the watermark at which it last took a match and is evicted one timespan after that. For events evaluated in order the watermark is the match's own time, so nothing changes and the reference run is the same; `late-hosts.test.ts` covers a clock 30 minutes and a day behind, a backlog in two requests, and the window still closing after a pause longer than the timespan. Not changed: a match more than 60 seconds older than the newest match of its group is ignored, so a rule that groups by address alone does not combine a late host with a punctual one.

## S12-09 — The two findings the review left open are not fixed on this branch (2026-11-15, S12)

The review ([S12-review.md](S12-review.md)) fixed six defects and left two open, because each repair is a choice about the design: S12-R08, a failed alert write loses the alerts of events that were already acknowledged, and S12-R09, the checkpoint's position assumes that ids only grow.

- **Nothing sends with `ack=stored` yet.** The upload page and the command line always wait for detection, and with only such senders no acknowledged event waits in the buffer: a request whose evaluation fails carries its own events, answers 500 and is sent again, as in version 0.1. The loss S12-R08 describes needs a sender that is answered before its events are evaluated, and the first one is the shipper of S14. S12-R08 must be closed before S14.
- **S12-R08 belongs with the ingest contract.** What a sender is told when Centinela cannot finish, and when it should send again, is what S11 defines (503, 429). Choosing there between retrying the write, replaying from the checkpoint and answering `ack=stored` for what was stored keeps that contract in one session.
- **S12-R09 changes the id contract.** It needs a position that does not follow the clock, such as a sequence column, or a floor on the timestamp of new ids. S18 reworks the events table and is the natural place.

Both stay in the known gaps of `docs/DETECTION.md` until then. Which session takes each is David's to confirm in the plan.

## S12-10 — Web tests wait up to five seconds for an element (2026-11-15, S12)

The pull request's first CI run failed in a test this session did not touch: `alerts.test.tsx`, "opens an alert with the keyboard", could not find the heading of the alert page. The same commit had passed seven minutes earlier. Testing Library waits one second for an element by default, and that page loads its data after a navigation; on a busy two-CPU runner it can take longer. Running the file on one CPU shared with four busy loops reproduces the failure three times out of three, in that test and in another of the same file.

`packages/web/test/setup.ts` now sets the wait to five seconds and the web project's test timeout is twenty, as the server's already was. A test that passes is not slowed down, because the wait ends as soon as the element is there. With the change the same file passes three times out of three under the same load. The tests this session added make the runner busier, which is the likely reason the failure showed up now; the cause was already there. Both files are outside the session's paths.
