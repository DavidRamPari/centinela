# Session S11 decisions

S11 builds ingest v2: the part of the phase 1 contract that was ARCHITECTURE §16.2 and is now §2.3, §4, §5.3, §8.2, §9, §12 and §15. A shipper can send gzip batches, is told to wait when the server is behind, and can be limited to its own sources and hosts. Rules find field names without regard to case, and a failed alert write no longer loses alerts (S12-R08). Files touched outside the paths the session owns are listed in S11-08.

## S11-01 — An NDJSON line becomes what the source's parser reads (2026-11-20, S11)

`Parser` gains `input: 'line' | 'object'`. A JSON string is passed on as it is for both kinds. An object is its `message` for a `line` source and its own JSON text for an `object` source. Anything else is `invalid NDJSON line`. This closes S5-09: a Sysmon event that a shipper wraps with a `message` key now reaches the Sysmon parser whole.

- **The object's own text, not a re-serialization.** The parser gets the line exactly as it arrived (trimmed), so key order and number spelling are what the shipper sent. An NDJSON line holds no raw newline, so it stays one line.
- **A line source without `message` gets its own reason.** `no message in object` tells the operator that the shipper sent the wrong shape, where `invalid NDJSON line` would suggest broken JSON. A `message` that is not a string or is blank counts as missing.
- **Blank strings stay rejected.** A JSON string that is only spaces was rejected before S11 and still is; a blank NDJSON line is still skipped without being counted.

## S11-02 — gzip goes through the body parser, behind an allowlist of encodings (2026-11-20, S11)

Express's text parser already inflates `gzip`, `deflate` and `br` bodies and applies its limit to the inflated bytes. The router checks `Content-Encoding` first and answers `415` for anything but `identity` and `gzip`, so the contract's single encoding is what is accepted.

The limit is enforced as the body inflates: once 5 MB of output is reached, the parser stops inflating, discards the rest of the request without inflating it and answers `413`. The answer comes after the client has finished sending, not before. Closing the connection early would save the bandwidth, but a shipper would then see a connection error, which it retries, instead of a `413`, which tells it to send smaller batches. Measured on the development machine with a body of 10 MB that inflates to 10 GB: the server answers `413` in about 0.1 s, while inflating all of it takes 28.6 s. The acceptance test sends that body and fails if the answer takes more than 5 s.

## S11-03 — Scoped tokens, and where a line's own host is checked (2026-11-20, S11)

- **Storage.** `allowed_sources` and `allowed_hosts` are `text[]`, empty by default (migration 005). Hosts are stored lower-cased; the API drops repeats and accepts at most 100. A host entry is a name in the characters the ingest query accepts, optionally ending in `*`; a lone `*` is allowed and means what an empty list means.
- **Comparison.** Only A to Z fold, and patterns are compared as text (`startsWith`, `===`). `İnfra` does not match `i*`, `aXb` does not match `a.b*`, and a host made of regex syntax is plain text.
- **The request.** A scoped request is checked after the query is validated and before the body is read (`403`). A request without `host` is for `unknown`, which a token scoped to hosts does not allow: a scoped token must name its host.
- **The line.** The router passes the check as a function, `IngestContext.acceptsHost`, and the orchestrator applies it right after parsing. A function keeps the pipeline free of the ingest layer's types. The event is rejected with `host not allowed for this token` before its timestamp is checked or an id is spent on it.
- **"Counted".** A refused line is counted in the answer (`rejected` and its sample) and in the stream's `rejected` counter. A refused request (`403`) is counted only in the request log, with its path and query; a per-token count of refused requests is left for the hosts page (S14), which reads the streams.

## S11-04 — Limits: per token, per address before the token is looked at, and a bound on requests in progress (2026-11-20, S11)

- **Per token.** `RATE_LIMIT_INGEST_PER_MINUTE` applies to each stored token, and `INGEST_TOKEN` has one budget of its own. The upload route keeps its per-address limit: it is behind the dashboard session.
- **Requests without a valid token, per address, checked before the token.** §16.2 said these requests are limited per address. Counting them is not enough to slow guessing: if a correct guess still went through after the limit, the limit would slow nothing. So an address that sent `RATE_LIMIT_AUTH_PER_MINUTE` requests without a valid token in its current minute is answered `429` until the minute ends, whatever token it then sends. The cost is that a good shipper behind the same address as a guesser waits too; that is the same trade-off the sign-in lockout makes.
- **A small counter of its own.** Both limits use a fixed one-minute window per key in `security/rate-limit.ts` instead of `express-rate-limit`, because the per-address one counts only failures and must be checked before the token is verified. The table is bounded at 100,000 keys: expired windows go first, then the oldest. These answers carry `Retry-After`, not the draft `RateLimit` headers.
- **In progress, not waiting.** §16.2 counted requests waiting for the pipeline. The router counts requests from the moment they pass the checks until they are answered: reading the body, waiting, being processed. That is what a single counter can see, and it also bounds the memory held by bodies being read. With `INGEST_MAX_PENDING` (16) in progress, the next request is `503` with `Retry-After: 5`, before its body is read. Five seconds is a few batches of work; a shipper that honours it comes back when the queue has moved. Uploads are not counted.

## S11-05 — Field names: exact first, then a comparison that allocates nothing (2026-11-20, S11)

`EventView.value` returns the field with the rule's exact spelling when the event has it. Only when it does not, it walks the event's keys in their own order and returns the first one equal to the rule's name without regard to A to Z case, comparing lengths first. Every way a rule names a field goes through `value`, so detection items, `fieldref`, `group-by` and `condition.field` all follow the rule. `npm run rules:lint` lower-cases field names in ASCII before its field checks and groups `Image` and `image` as one field; it still reports 22 known findings and no new one.

A first version built a map of lower-cased keys on each event's first miss. On the Windows mix it lost 6 to 7%, more than the 5% the plan allows, because most process-creation rules name fields an event does not have. The comparison loop replaced it. Measured with `npm run bench` on two CPUs (`taskset -c 0,1`), three runs each:

| Mix | Before S11 | After S11 |
| --- | --- | --- |
| Windows, 200,000 events | 7,211, 7,310 and 7,240 events/s | 7,301, 7,354 and 7,126 events/s |
| Linux and web, 100,000 events | 76,351 and 80,341 events/s | 76,090 and 83,067 events/s |

The difference is within the spread between runs, and so is the whole pipeline's: `npm run demo` on two CPUs took 28.9 s and 28.5 s on `main` and 27.7 s and 29.4 s with S11, on the same machine and the same 201,317 events. The demo still creates the same 37 alerts and detects 19 of 19 scenarios, the SigmaHQ regression samples still match 272 of 276, and the repository's Windows rules raise the same alerts on loggen's Sysmon data whether its keys are lower-cased or not (`test/detection/field-names.test.ts`).

## S11-06 — Closing S12-R08: alerts that could not be written are held and written later (2026-11-20, S12-R08)

The review listed four repairs. The chosen one keeps the candidates of a failed write and writes them, in order and before any newer one, with the next write; it adds the bound and the place for what is dropped that the review asked for.

- **Why not the others.** Treating the failure like a crash (restore the checkpoint, replay) would make a failure that repeats fail every ingest call. Retrying the write once covers a deadlock or a dropped connection, not a failure that lasts several requests, which the acceptance asks for. Answering `ack=stored` calls for what they stored is part of the chosen repair, but on its own it would still lose the alerts.
- **No call fails for it.** The events of the failed step are stored, so the request that hit the failure answers `200` for what it stored, with `ack=stored` or not: a sender told to send again would store its events twice. The alerts are written by the next write: the next batch with candidates, the end of the next call, the idle release (its timer is also armed when only alerts wait), `drain` or the checkpoint. Held alerts alone are tried once per queued task, so a request does not repeat a write that just failed.
- **A candidate the database refuses is dropped, not held.** When PostgreSQL refuses the data itself (any SQLSTATE outside classes 08, 40, 53, 57 and 58), the batch is written one candidate at a time; those it refuses are dropped and reported, the rest are written, and a later candidate that fails for another reason is held with everything after it. Errors that are not PostgreSQL answers (a dropped connection, a pool timeout) are held.
- **The bound.** At most 10,000 candidates are held; past that the oldest are dropped and reported. `onAlertWriteError` hears every failure with what is held and what was dropped; the server and `npm run ingest` log it.
- **No checkpoint while alerts are held.** The held candidates exist only in memory. The last checkpoint is still before their events, so a restart evaluates those events again and raises the alerts; their `count` can then include matches twice, as after a crash. Saving a checkpoint first tries to write them.
- **`drain()` fails while alerts are held**, so `npm run ingest` and `npm run demo` exit with an error instead of ending without their alerts.
- **Known limits.** A write whose commit succeeded but whose answer was lost (the connection dropped after `COMMIT`) is held and written again, so that alert's `count` and events are added twice. The call that finally writes held alerts counts them in its own `alertsCreated`, although they came from earlier events.

Tested with the memory sink failing once and failing 38 requests in a row on the small demo delivered live: the alerts are those of the run without failures (`test/pipeline/alert-write.test.ts`). With the old behaviour, 9 of that file's 18 tests fail.

## S11-07 — Streams are tied to the token that delivers them (2026-11-20, S11)

`verifyIngestToken` returns the credential (the stored token's id and its scope) instead of a boolean, and the router passes the id as the stream's `tokenId`. The bound of 1,000 streams now counts per token; `INGEST_TOKEN` has no row, so its streams keep a null `token_id` and share one bound. This closes the gap S12-04 left.
