# Session S2 decisions

## S2-01 — Sigma strings follow pySigma's `SigmaString` exactly (2026-10-26, S2)

`*` and `?` are wildcards; `\*`, `\?` and `\\` are literal `*`, `?` and `\`; a backslash before any other character is a literal backslash. So `C:\Users\*` is the literal text `C:\Users*`, and a wildcard after a backslash needs `\\*` — which is how SigmaHQ writes it (`'\\Users\\*\\Downloads\\'` in `proc_creation_win_rundll32_udl_exec.yml`, `'\\\*.dll'` for a literal star in `proc_creation_win_cmd_del_greedy_deletion.yml`). Case-insensitive matching lower-cases both the pattern (at compile time) and the value (once per event and field) with `toLowerCase()`; `?` is one UTF-16 code unit. Field names are matched exactly (case-sensitive), as in the Elastic and Splunk backends. No regular expression is ever built from a rule value: wildcard patterns compile to `===`, `startsWith`, `endsWith`, `includes`, or a segment matcher that is linear per segment.

## S2-02 — Modifier chains (2026-10-26, S2)

Modifiers apply left to right, as in pySigma. Type modifiers (`re`, `cidr`, `exists`, `lt`/`lte`/`gt`/`gte`, `fieldref`) must come first; a type modifier after a string transform, a transform after a type modifier, or `cased` on a non-string type is `modifier:incompatible`. `re` sub-modifiers are `i`/`ignorecase`, `m`/`multiline`, `s`/`dotall`; elsewhere they are `modifier:unknown`. Details where ARCHITECTURE §5.3 is silent:

- Encoders (`wide`/`utf16le`, `utf16be`, `utf16`, `base64`, `base64offset`) need a value without wildcards (`modifier:wildcard-encoding`); pySigma refuses wildcards for base64 too. `utf16` writes the byte order mark `FF FE` and little-endian units (Python's `utf-16` on every common platform). `base64offset` uses the byte length of the value in pySigma's offset formula; for ASCII values, all that SigmaHQ uses, this is pySigma's result (tested with its `foobar` vectors).
- **Deliberate deviation:** values produced by `base64`/`base64offset` match case-sensitively, although strings are case-insensitive by default. Base64 is case-significant (case-folding `QQBkAGQA` matches different bytes), and SigmaHQ rules list each case variant of the plain text explicitly (`proc_creation_win_powershell_base64_mppreference.yml` lists `Add-MpPreference ` and `add-mppreference `).
- `null` combined with a transform, or as a keyword, is `detection:null-with-modifier`. `exists` needs a YAML boolean. Numeric comparisons need a numeric rule value and read numbers or numeric strings from the event; anything else never matches. `fieldref` compares the two fields' string forms case-insensitively and honours `all` with several references.
- `cidr` accepts IPv4 and IPv6 networks; an IPv4-mapped IPv6 address in the event is compared as IPv4; field values that are not strict addresses (`0x0a.1`, host names) never match.
- Keyword values are wrapped in `*…*` after every other transform, so `'|all'` and `'|re'` keyword keys work.

## S2-03 — `windash` is a character class, not an expansion (2026-10-26, S2)

pySigma expands every option dash into five variants and builds every combination (5^k strings for k dashes). The engine marks each such position (pySigma's `\B[-/]\b`, applied per text part) as a class matching any of `-`, `/`, `–`, `—`, `―`. That accepts exactly the same strings (each position varies independently) without exponential growth. The class is searched with `indexOf` on the longest literal run of its segment.

## S2-04 — Regexes: `re2-wasm` works, no fallback needed (2026-10-26, S2)

`re2-wasm` 1.0.2 loads synchronously from ESM, rejects backreferences and lookaround (`regex:not-re2`), supports `(?i)` inline flags, and runs `(a+)+$` against 8,000 characters in milliseconds (tested). All 67 `|re` items in the vendored rules compile, so D-007's fallback (native `RegExp` with a static ReDoS check) is not used. Patterns always run with RE2's `u` flag, against the value truncated to 8,192 characters.

## S2-05 — Loading: load errors versus unsupported rules (2026-10-26, S2)

YAML is parsed with the `yaml` package (YAML 1.2 core schema, `uniqueKeys: true`), so dates such as `2022-12-21` stay strings. A file whose header does not validate (title, GUID id, level), that is not YAML, has duplicate keys or reuses an earlier id is a **load error**: it has no `RuleMeta` and the report lists it under "Load errors" (ids must be unique for the rules API). A valid header with an unsupported construct stays in the rule list with `supported: false`: `status:deprecated`/`status:unsupported`, `yaml:multi-document` (metadata from the first document), `rule:missing-logsource`, `rule:missing-detection`, `rule:duplicate-name` (a later rule reusing a `name` that correlations reference), and every compiler reason. Reason strings are `code` or `code (detail)`; the report groups by code. `level` is required (every SigmaHQ rule has one). Files above 1 MB are refused (`file:too-large`) and symbolic links are not followed, so rules only come from inside `rules/`.

## S2-06 — Correlation details (2026-10-26, S2)

Beyond ARCHITECTURE §6:

- `timeframe` is accepted as an alias of `timespan` (later versions of the Sigma correlation specification use it); both at once, a missing or zero timespan is `correlation:timespan`. `aliases` is unsupported (`correlation:aliases`). `temporal`/`temporal_ordered` with a `condition` are unsupported rather than guessed. Thresholds are non-negative integers.
- `value_count` keeps only the newest match per distinct value, so the window holds at most one entry per value and the count is its size. Each group keeps at most 1,000 matches and each correlation at most 100,000 groups (oldest dropped first): attacker-chosen IPs and user names cannot grow memory without bound.
- Contributing events are the most recent 100, oldest first. For `temporal_ordered` they start at the earliest complete sequence (an earlier unrelated success does not show up in the alert). A chained firing carries its events into the outer correlation, so `centinela-ssh-bruteforce-success` links the failures and the success.
- The candidate's `host` is the group's `host.name`, else the host shared by every contributing event, else null; entities are the contributing events' `srcIp`, `user` and `host` (at most 100 each). Group keys use the spec format; the in-memory window key is a JSON array, so a user name containing `,host.name=` cannot merge two groups' windows.
- Building blocks are computed over *supported* correlations: a Sigma rule referenced only by an unsupported correlation keeps alerting instead of going silent. `generate` defaults to false (ARCHITECTURE §6).
- The watermark is the newest event time seen by the detector; groups are swept each time it advances 60 s and on `flush`. Conditions are evaluated on every match, so `flush` never has pending matches and returns `[]`.

## S2-07 — `createDetector`: lazy, memoized rule sets; per-engine enabled flags (2026-10-26, S2)

`createDetector({ rulesDir })` returns a `DetectionEngine` (a `Detector` plus `ruleSet`, `rules()`, `setRuleEnabled(id, enabled)` and `watermark`). Rules are read and compiled on first use and memoized per folder, because `createPipeline()` runs in many tests that never ingest and compiling ~1,250 rules takes 1–2 s. Correlation state and enabled flags belong to each engine; the compiled rule set is shared and never mutated after loading. Disabling a correlation clears its windows. S4 persists flags in `rule_state` and calls `setRuleEnabled`. `AlertCandidate.rule` objects are shared snapshots; consumers must not mutate them.

## S2-08 — Performance: shared predicates, a literal index and a prefilter (2026-10-26, S2)

A Windows process-creation event is routed to 1,193 rules; evaluating each one costs about 1 ms per event (about 900 events/s). Three measures, all in `src/detection/`:

1. Identical selections and detection items across rules compile once and are evaluated at most once per event (a slot in `EventView.memo`).
2. Every case-insensitive literal pattern (`v`, `v*`, `*v`, `*v*`) of each field goes into a per-rule-set `LiteralIndex`: a map, a trie, a reversed trie and an Aho–Corasick automaton. Each field value is scanned once per event and rule checks become set lookups.
3. Each rule gets a required-literal set derived from its condition (AND keeps the smallest child set, OR the union, NOT and non-literal items give none). The engine evaluates only rules whose required literals matched, plus the 24 Windows rules that have none. Tests compare the result with exhaustive evaluation on both bench mixes, and every modifier test runs with and without the cache.

`npm run bench` on the cloud VM: Linux/web mix about 60,000–73,000 events/s, Windows mix about 5,600 events/s (from about 900).

## S2-09 — Golden test semantics (2026-10-26, S2)

Every object of every regression file is evaluated against the rule named by the file (`<rule id>.json`), routed as `{product: windows, category: process_creation}`, with `Event.EventData` as `fields`. 272 of 276 events match (98.6%). The 4 misses are context events in two `findstr` samples (the parent `cmd.exe` and the piped `icacls`/`net` process) whose `info.yml` expects one match per file. The report therefore also shows a per-file result: a file passes when at least `match_count` (largest in `info.yml`, default 1) of its events match. 267 of 267 files pass. The decoder for files with several objects is `src/detection/json-stream.ts`, reusable by S5.

## S2-10 — Rule layout and links (2026-10-26, S2)

Centinela's base rules live in `rules/centinela/linux/` and `rules/centinela/web/` (S5 adds `rules/centinela/windows/`); correlations live in `rules/correlation/`. Every rule has `author: DavidRamPari`, `status: experimental`, a description, references to ATT&CK, false positives and ATT&CK tags. `centinela-ssh-bruteforce` keeps the id from the ARCHITECTURE §6 example. Base rules carry technique tags too (e.g. `T1110` on `centinela-ssh-auth-failure`) so the ATT&CK coverage view counts them. Centinela rules get `url: null`: ARCHITECTURE §3.3 defines the URL only for SigmaHQ rules, and the repository URL is not part of the contract.

## S2-11 — CLIs, report and tests (2026-10-26, S2)

`npm run rules:report` and `npm run bench` default to `<repo>/rules` (`--rules-dir` overrides; relative paths resolve against `INIT_CWD`), not `RULES_DIR`, because they describe the repository's rules and must not depend on server configuration. Options are validated with zod; bad arguments exit with code 2. The report carries no timestamp, so `docs/rules-report.md` only changes when rules or the engine change. The bench mixes are deterministic: real auth.log and nginx lines through S1's parsers (routine traffic plus brute force, scanning and SQL injection), and Sysmon process creation with nine routine processes per regression sample. Rule loading and event construction are not timed, and each mix gets a 5,000-event warm-up.

Tests live in `packages/server/test/detection/` (the server's Vitest config only includes `test/**`). `test/cli-stubs.test.ts` was deleted: both of its rows were S2's stubs, and S0's instruction was to delete rows as sessions implement them. `test/detection/scenarios.test.ts` runs loggen's small and default samples through the parsers and the detector (every scenario detected, no high/critical alert from background traffic), importing loggen by relative path as S1's tests do, so `package.json` and the lockfile stay untouched.
