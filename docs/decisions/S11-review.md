## S11-R01 — A place among the requests in progress could be kept for good, or given back too early (2026-11-20, S11 review)

Fixed in `9a413d3`. Severity: high: one token holder, scoped or not, could stop all ingest until the server restarted, and the bound on requests in progress did not bound them. `limitInProgress` gave a request's place back on the response's `close` event, listened for when the place was taken. That went wrong three ways:

- A client that left while its token was checked (a database round trip for a stored token) had closed its connection before the listener existed, so `close` never came and the place was kept for good. After `INGEST_MAX_PENDING` (16) such requests every request was answered `503`. Shown through the test app with a stored token whose row the test holds locked, so that the check waits: before the fix the next request is `503`.
- A pipelined request (HTTP/1.1 lets a client write its next request before the first is answered) is given the connection only when the answer before it is done. When the connection closes first, its `close` never fires either. Shown with two requests in one write: afterwards one of the two places was gone.
- A client that left while its request waited for the pipeline gave the place back at once, while the request still held its body and its turn in the queue. With a bound of 2, ten requests whose clients left reached the pipeline together, each with its body in memory.

The place is now given back when the server is done with the request: when its pipeline call settles, through the route's error handler when it fails before that (the body parser's `400` or `413`), or when the request closes before its body arrived whole. The last case matters for gzip: when a request is aborted, the inflating stream it is piped into is never ended, so the body parser never calls back. A request whose client is already gone takes no place and is not processed. ARCHITECTURE §9 (check 6) and S11-04 say so. Tests, in `test/ingest/in-progress.test.ts`: "keeps no place for a client that left while its token was checked", "gives back the place of a pipelined request whose client left" and "keeps the place of a request whose client left while it waits for the pipeline" fail before the fix; "gives back the place of a gzip body whose client left before sending all of it" fails when the fix leaves out the `close` case.

## S11-R02 — A write refused for the server's state dropped the alerts instead of holding them (2026-11-20, S11 review)

Fixed in `e8ec280`. Severity: medium: it brings back the loss of S12-R08 for common failures. `isTransientWriteError` held a failed write only for the SQLSTATE classes 08, 40, 53, 57 and 58 and took every other answer from PostgreSQL for a refusal of the data, so the candidates were written one at a time and each was dropped. A read-only standby during a failover or `default_transaction_read_only` during maintenance (25006), a lock timeout (55P03), a refused password after a rotated secret (28P01), an internal error (XX000) or a missing table (42P01) say nothing about the alerts. Shown against PostgreSQL with a sink whose connections are read-only for one write: both alerts of the step were dropped, and neither existed once the database was writable again. Now only the classes in which PostgreSQL refuses the data drop a candidate: 22 (data exception), 23 (integrity constraint violation) and 54 (program limit exceeded; a dedup key longer than the index allows is one, and holding it would block every later alert). Every other failure is held. ARCHITECTURE §2.3 and S11-06 named the old classes. Tests, in `test/pipeline/alert-write.test.ts`: five new rows of "which failed writes are worth repeating" and "holds the alerts while the database is read-only and writes them once it is not" fail before the fix.

ARCHITECTURE §2.3 also said that a held write is tried at most once per queued task. Held candidates alone are; a write of newer candidates in the same task tries them again first. The sentence now says so; the code did not change.

## S11-R03 — Guesses sent at once got past the per-address limit (2026-11-20, S11 review)

Fixed in `90cae1a`. Severity: low: stored tokens have 256 bits, so the limit is a second line of defence. `requireBearerToken` read the address's count before looking the token up and added to it after. A stored token is looked up in the database, so guesses sent at once were all checked while none had been counted. Against the test app and PostgreSQL, 200 concurrent guesses from one address with `RATE_LIMIT_AUTH_PER_MINUTE=5` were checked 21 times; with the fix, 5 times. A request now counts from before its token is checked and takes its count back when the token is valid or cannot be checked. The cost: when more requests from one address than the limit are checked at the same moment, the extra ones are answered `429` even with a valid token. A check takes about a millisecond, so a shipper meets this only when the database is slow. ARCHITECTURE §9 (check 1) says so. Tests: `test/ingest/bearer.test.ts`, "counts a guess while its token is checked, so guesses sent at once stop at the limit" fails before the fix, and its two other tests hold the count's return for a valid token and for a failed lookup; `test/security/rate-limit.test.ts`, "takes a count back only in the window it was made in".

## S11-R04 — A full counter table cost a scan of every key for each new one (2026-11-20, S11 review)

Fixed in `2188e31`. Severity: low. The window counter keeps at most 100,000 keys. Once they were all live windows, which an IPv6 client has addresses enough to make, each new key scanned the whole table for expired windows: 1.0 ms of one CPU per request without a valid token from a new address. Windows sit in the map in the order they started, so the scan now stops at the first live one, and a new key costs about a microsecond. Test: `test/security/rate-limit.test.ts`, "stays cheap for a new key when the table is full of live windows": 2,000 new keys took 2.0 to 2.7 s before the fix and must take less than 250 ms.

## S11-R05 — Fixed after the review: one token could hold every place in progress (2026-11-20, S11 review)

Severity: medium. A request keeps its place while its body is read, and nothing bounds how long that takes except Node's `requestTimeout`, 300 seconds by default. A token holder that opens `INGEST_MAX_PENDING` requests and writes their bodies slowly keeps every place, so every other shipper is answered `503` for five minutes, and it can start again; a scoped token can do it as well as `INGEST_TOKEN`. The compressed size of a gzip body has no bound of its own either: 60 MB of empty gzip members were read and inflated in 0.26 s and answered `200`, and a slow sender can make such a body last as long as the deadline allows. Before S11 a slow client cost memory and a socket but did not stop the others. Options: give each token at most a share of the places; give ingest bodies a deadline of their own, seconds rather than minutes, answered `408`; bound the compressed size as well. Each changes what a shipper sees, so the choice is left for a decision. `docs/THREAT_MODEL.md` lists it among the residual risks.

Decided by the S11 session after this review: each token gets a share of the places (`INGEST_MAX_PENDING_PER_TOKEN`, 4 by default), and the other two options are not taken. See `docs/decisions/S11.md`, S11-09.

## S11-R06 — Open: an IPv6 client gets a budget of guesses per address (2026-11-20, S11 review)

Severity: low. Requests without a valid token are counted per client address. An IPv6 client usually holds a /64 or more, so it can send each guess from a new address. Before S11 the ingest route used `express-rate-limit`, which groups IPv6 addresses by /56 by default and still does for `/api/auth/*` and uploads. Counting IPv6 clients by prefix would restore that. Which prefix is a decision, and the sign-in lockout (S6) counts whole addresses too, so it is left open.

## S11-R07 — Checked and left as it is (2026-11-20, S11 review)

- **The order of the checks.** A request without a valid token, a token past its budget, a bad query, an unsupported content type or encoding, a scope refusal and a busy server are all answered before the body is read, on a listening server. A request answered `503` still uses one of its token's budget; that is the order ARCHITECTURE §9 states.
- **Content-Encoding.** `gzip` and `GZIP` are accepted; `x-gzip`, `br`, `deflate`, `compress`, `gzip, gzip`, `gzip, identity`, `identity, gzip` and an empty header are `415` (two headers arrive joined, as `gzip, gzip`). A truncated stream, a body that is not gzip, deflate data labelled gzip and a member followed by garbage are `400`; two members and a member followed by zero bytes are read. A body that inflates to exactly 5 MB is accepted and one byte more is `413`; after a `413` the rest of the request is read off without being inflated, as S11-02 says (body-parser 2.4.0 unpipes and destroys the inflating stream). A byte order mark at the start of a body is removed by the decoder, for text and for NDJSON. A content type that the router accepts and the body parser would not read would be answered `200` with nothing read; nine unusual ones were tried (a parameter without a value, `;;`, an unclosed quote, a tab before `;`, among others) and every one was read.
- **NDJSON.** The table of ARCHITECTURE §9 was checked value by value against both input kinds, plus arrays nested a million deep, objects nested 100,000 deep, a Sysmon value nested 12,000 deep, `__proto__` and `constructor` keys, lone surrogates and NUL characters: each is rejected with a reason or parsed, and nothing throws past the orchestrator. `{"__proto__":{"message":"x"}}` has no `message`.
- **Scoped tokens.** Patterns are validated by a fixed regular expression, stored as parameters, compared with `===` and `startsWith` on a copy of the host with only A to Z lower-cased, and never compiled. Values read back from the database are checked to be arrays of strings; one that is not lower-cased or holds another character can match nothing, so it fails closed. The line check covers the host each parser takes from the line (the syslog header, Sysmon's `Computer`, nothing for web logs, which take the request's host) after it is cut to 255 characters, as stored. An event without its own host takes the request's host, which was checked.
- **Field names.** `asciiEqualIgnoringCase` folds only letters (`@` and `` ` ``, `[` and `{`, `İ` and `i`, the Kelvin sign and `k` stay apart); `Object.hasOwn` and `Object.keys` keep prototype keys out. Detection items, `fieldref`, numeric comparisons, the literal prefilter, `group-by`, `condition.field` and the dedup entity all go through `EventView.value`. The Windows bench was run on two CPUs (`taskset -c 0,1`), alternating `main` and this branch three times each with 200,000 events: 8,517, 9,701 and 8,636 events/s on `main`, 8,576, 8,548 and 9,130 on the branch, with the same 38,675 alert candidates. The medians are 0.7% apart, inside the spread between runs of one side, so the bound of 5% holds.
- **Held alerts.** No checkpoint is saved while alerts are held, and saving one first tries to write them. Held alerts alone are tried once per queued task; with idle time they are tried once per `REORDER_IDLE_MS` (at least 100 ms by configuration, 5 s by default), not in a tight loop. A restore that fails after holding alerts and is tried again writes those alerts and evaluates their events again, so an alert's `count` can include a match twice: the at-least-once behaviour S12-R02 describes. `publish` runs inside the same `try` as the write, so a publisher that threw after a successful write would have the alerts written twice; the SSE hub does not throw (a write to a closed stream fails later, through the stream), so this cannot happen today.
- **Streams.** The token's id reaches `ingest_streams.token_id` and `INGEST_TOKEN` keeps a null one. Host names that differ only by case are separate streams, so a token scoped to `web-01` can create a few of them; the bound of 1,000 still holds.
- **The dashboard form** validates hosts with the shared schema before sending them, shows the refusal in both languages and the scope of each token as text.
- **The acceptance tests** were run against mutated copies of the code in a scratch clone: without the per-address check before the token, with one budget for every token, without the token id on streams, without the line host check, without the request host check, with field names matched exactly, with every encoding the body parser knows, with the in-progress check after the body, with the limit on the bytes sent instead of the bytes inflated, with an NDJSON object read as its `message` for an object source, with a failed write dropping its alerts, and with a checkpoint saved while alerts are held. Each mutation failed the tests that name it. A refused request is "counted" only in the request log (S11-03); no test reads that log.

Not checked: a real shipper (Fluent Bit) against `429`, `503` and `Retry-After`; a real PostgreSQL failover, as opposed to `default_transaction_read_only`; memory with 10,000 held alerts of 100 events each; the form in a real browser; GitHub's runner, where David runs CI by hand.
