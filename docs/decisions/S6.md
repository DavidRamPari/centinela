# Session S6 decisions

## S6-01 — Every route needs the session unless it is explicitly public (2026-10-26, S6)

`createApiRouter` mounts, in order: health → ingest (its own credentials) → `/auth` (sign-in is public) → session guard and CSRF check → JSON body parser → every resource router. Anything mounted after the guard, including S7's playbook route and routes added later, needs the session without further code. Public: `GET /api/health`, `POST /api/ingest` (bearer token) and `POST /api/auth/login`. Without a session, unknown paths answer `401`, not `404`, so the API does not reveal which routes exist, and bodies are never parsed for anonymous requests. `test/auth/protected-routes.test.ts` reads the endpoint list from ARCHITECTURE §9 and checks `401` without a session (and with an unknown one) for every non-public endpoint, and `403` without the CSRF header for every state-changing one, so a contract row added by another session is covered automatically.

## S6-02 — Server-side sessions keyed by an HMAC of the token (2026-10-26, S6)

The cookie carries 32 random bytes (base64url). `admin_sessions` stores HMAC-SHA256(`SESSION_SECRET`, `session:` + token) as its key, so a dump of the table cannot be replayed and rows cannot be forged without the secret; rotating the secret signs everyone out. Lifetimes are configuration: idle `SESSION_IDLE_MINUTES` (120) and absolute `SESSION_MAX_HOURS` (12, at most 168 so the stream timer below stays within `setTimeout`'s range). `last_seen_at` is written at most once a minute (one statement: a CTE reads the live session and conditionally updates it). `GET /api/auth/me` checks without touching, because the dashboard polls it every minute to notice expiry; polling must not keep an idle session alive. Signing in deletes the session the browser already held (no fixation, no pile-up) and purges expired rows. A session whose user name is no longer `ADMIN_USERNAME` is refused.

## S6-03 — Cookies are always `Secure`, with the `__Host-` prefix (2026-10-26, S6)

`__Host-centinela` (session, `HttpOnly`) and `__Host-centinela-csrf` (readable), both `Secure; SameSite=Strict; Path=/`, `Max-Age` = the session's maximum age, cleared with the same attributes on sign-out. As PLAN requires, `Secure` is set in every environment: browsers accept it on `http://localhost` and `http://127.0.0.1`, which covers `npm run dev` and Docker Compose. Plain HTTP through another host name does not work; `docs/SECURITY.md` says so.

## S6-04 — CSRF: double submit bound to the session (2026-10-26, S6)

The CSRF token is HMAC-SHA256(`SESSION_SECRET`, `csrf:` + session token), set as the readable cookie at sign-in and re-issued by `GET /api/auth/me`. A state-changing request passes only when `X-CSRF-Token` equals the cookie and the value derived from the session cookie (OWASP's "signed double-submit"), compared in constant time without short-circuit. A token from another session is refused even when header and cookie agree. Exempt: sign-in (no session yet; it reads JSON only, which an HTML form cannot send cross-site, and `SameSite=Strict` applies) and `POST /api/ingest` (bearer token, no ambient credentials). The dashboard reads the cookie at request time (S4's client), so tabs and re-sign-ins stay consistent.

## S6-05 — Sign-in protection: per-IP lockout in memory, constant work (2026-10-26, S6)

`LOGIN_MAX_FAILURES` (5) failures from one client IP within `LOGIN_LOCKOUT_MINUTES` (15) lock that IP for the same time; the failure that reaches the limit already answers `429` with `Retry-After`, a locked client is refused before any password work, and success clears the record. The lockout is per IP, not per account: an account lockout would let anyone lock the only admin out. State lives in memory (one process, D-003; restarts clear it) with at most 10,000 tracked clients. `/api/auth/*` also has a rate limit (`RATE_LIMIT_AUTH_PER_MINUTE`, 30). The password is always verified and the user name compared in constant time, so a wrong user name costs the same as a wrong password. At most 4 argon2id checks run at once (64 MiB each); more answer `503` with `Retry-After: 1` rather than queueing. Failed sign-ins are audited with the attempted user name (attacker-chosen: cut at 256 characters, shown as text), and the transition to locked as `auth.lockout`.

## S6-06 — Admin credentials, development defaults and production refusals (2026-10-26, S6)

Outside production the server falls back to `admin` / `centinela-dev`: the argon2id hash of that password and a development `SESSION_SECRET` are constants in `config.ts`, like S0's development ingest token. The server logs a warning naming the development credentials when it uses them, and `npm run demo` prints the sign-in at the end, so local use needs no setup. Production requires `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH` and `SESSION_SECRET` and refuses the development hash, any non-argon2id hash, argon2id below OWASP's minimum (m = 19456 KiB, t = 2), and secrets shorter than 32 characters or equal to the development value. Because checking a password needs the asynchronous argon2 module, `loadConfig` (synchronous) compares the hash string, and `src/index.ts` additionally verifies at start-up that the configured hash does not accept the development password (a re-salted development hash). `npm run hash-password` reads the password twice without echo on a terminal or from the first line of standard input, never from arguments; it refuses fewer than 12 characters and the development password, and prints a single-quoted `.env` line because the hash contains `$`.

## S6-07 — Audit log: atomic where Centinela owns the write (2026-10-26, S6)

`audit_log` records `auth.login`, `auth.login_failed`, `auth.lockout`, `auth.logout`, `alert.triage`, `alert.bulk_triage`, `rule.update`, `token.create`, `token.revoke` and `ingest.upload`, with actor, target, client IP and a small `details` object. Alert triage and token changes write their row in the same transaction as the change; for that, S4's `triageAlert`/`triageAlerts` accept a `PoolClient` as well as a `Pool` (a type change only). Rule enable/disable and uploads are audited right after the change: the rule catalog owns its `rule_state` write and the pipeline commits per batch, so making them atomic would mean reworking S4's modules; the gap is listed as a residual risk. Rule toggles are recorded although PLAN only names triage, tokens and logins: they change what Centinela detects. `at` is written from the application clock with millisecond precision, so keyset cursors (`at|id`, S4's cursor helpers) round-trip exactly; the application never updates or deletes audit rows. `GET /api/audit` lists newest first with an optional `action` filter.

## S6-08 — Ingest tokens: SHA-256 at rest, environment token kept (2026-10-26, S6)

Secrets are `cnt_` + 32 random bytes in base64url; only their SHA-256 is stored (high-entropy secrets need no slow hash, and lookups stay one indexed equality). The first 12 characters are kept for display. Routes: `GET /api/tokens` (newest 200, revoked included), `POST /api/tokens` `{ label }` (`201` with the secret, shown once), `POST /api/tokens/:id/revoke` (idempotent; audited once). At most 50 active tokens; a transaction-level advisory lock makes the count and the insert atomic. `last_used_at` is written at most once a minute. Labels reject control and format characters (they reach the audit log and the dashboard). `INGEST_TOKEN` from the environment keeps working next to stored tokens: ARCHITECTURE §15 and S0-06 make it required in production, and scripts and the README rely on it. It is rotated by changing the variable; the dashboard says it exists.

## S6-09 — `POST /api/ingest/upload` in every environment, behind the session (2026-10-26, S6)

Supersedes the "not mounted in production" part of S1-05: with the session and CSRF required, the dashboard's upload works in production too. Order: rate limit → session → CSRF → query validation → content type → body parser, so unauthenticated uploads are refused before the body is read. Uploads are audited with source, host and counts.

## S6-10 — Rate limits come from the configuration (2026-10-26, S6)

Supersedes S1-05's constants: `RATE_LIMIT_INGEST_PER_MINUTE` (120), `RATE_LIMIT_UPLOAD_PER_MINUTE` (30) and `RATE_LIMIT_AUTH_PER_MINUTE` (30), one-minute windows per client IP, validated as integers. `createIngestRouter`'s override options are gone; tests set the variables. The limiter factory moved to `src/security/rate-limit.ts`, shared by ingest and auth. The constant-time comparison moved to `src/security/compare.ts`; `src/ingest/auth.ts` re-exports it as `tokensEqual` so S1's tests are unchanged, and `requireBearerToken` now takes an (async) verifier.

## S6-11 — API responses: nothing to render, nothing to cache (2026-10-26, S6)

`helmet` runs with `Content-Security-Policy: default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` and `X-Frame-Options: DENY` instead of its HTML-oriented defaults, and every response gets `Cache-Control: no-store` (the SSE hub still sets its own `no-cache`). The API serves JSON, problem+json and SSE only, so a stricter policy loses nothing.

## S6-12 — HTML policy defined once, applied by nginx and Vite (2026-10-26, S6)

`packages/web/security/headers.ts` (pure, so browser-typed tests can import it) defines the policy and the other headers. Production: `'self'` for every fetch directive, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`; no `'unsafe-inline'`, `'unsafe-eval'` or `data:` (the build has no inline script or style; checked). No `upgrade-insecure-requests`: it would rewrite `http://localhost` asset requests to HTTPS and break local use; HSTS belongs on the TLS terminator (S8). nginx: `nginx/security-headers.conf` is copied into the image and included in every location that serves files, because nginx drops inherited `add_header` lines in a location that sets its own; `/api/` is left to the API's headers. Vite: a plugin (`security/vite-plugin.ts`) sets the production headers on every `vite preview` response and, on the dev server, a development policy with a nonce random per process (`html.cspNonce`, which Vite puts on the React Refresh preamble, its client script and the `<style>` elements it injects) and `ws://localhost:*`/`ws://127.0.0.1:*` for HMR. `test/csp.test.ts` compares the nginx snippet with the definition, checks the template's locations and the Dockerfile copy, and starts real Vite dev and preview servers. The browser bundle sets zod's `jitless` mode first thing: zod otherwise probes `new Function`, which the policy blocks and reports. Verified by hand in Chromium (Playwright) through the real nginx template, on the Vite dev server and with `VITE_USE_MOCKS=true`: sign-in, every page, upload, token create/revoke and sign-out with no CSP violation.

## S6-13 — Dashboard: auth gate, `next` restricted, 401 handling in the client (2026-10-26, S6)

`/login` is public; every other route sits inside `RequireAuth`, which shows a loading state while `GET /api/auth/me` answers and redirects to `/login?next=<path>` when signed out. `next` must be a dashboard path (no `//host`, scheme, backslash or control characters): the sign-in page is not an open redirect. S4's client gained three things: the CSRF header on non-GET requests, `onUnauthorized` listeners called on any `401` (the gate clears cached data and redirects), and `retryAfterSeconds` on `ApiError` for the lockout message. Sign-in calls opt out of the `401` notification. The Security page (`/security`, in the sidebar) holds ingest tokens (secret shown once with a copy button; revoke asks for a second click instead of `window.confirm`) and the audit log. Everything lives in `src/features/auth/` except the route, nav and header lines, and `src/zod-config.ts`. MSW handlers for the new endpoints are in `features/auth/mocks.ts` and start signed in; with `VITE_USE_MOCKS=true` the mock accepts the development credentials.

## S6-14 — Live streams end with their session (2026-10-26, S6)

`GET /api/stream` sits behind the guard. Each stream is registered under its session: sign-out ends that session's streams, and a timer ends each stream at its session's absolute expiry. Otherwise an SSE connection opened with a stolen cookie would keep receiving alerts after the session was revoked. A stream is not ended when its session goes idle (listed as a residual risk); the dashboard's session poll notices within a minute and redirects.

## S6-15 — Tests sign in for real (2026-10-26, S6)

`createTestApp` (S4's helper) configures a test admin with a cheap argon2id hash and, by default, wraps the app so every request without a session cookie carries a real session row, both cookies and the CSRF header; `signedIn: false` sends requests as written. Existing route tests keep working unchanged, and S7's tests that use the helper will too, provided they use a test database: since the guard runs before routing, tests that used an unreachable pool (`errors`, `not-implemented`) now create a test schema, and the health test with an unreachable database passes `signedIn: false`. On the web side `renderApp` starts signed in (the session is seeded in the query cache), with `auth: 'fetch'` and `auth: 'signed-out'` for the gate's own tests.

## S6-16 — Shared files touched (2026-10-26, S6)

Outside S6's paths, kept minimal: root `package.json` (`hash-password`, `audit` scripts), `package-lock.json` (`argon2`), `packages/server/package.json` (`argon2`, `hash-password` script), `packages/shared/src/index.ts` (one export) and the new `packages/shared/src/auth.ts`, `docs/ARCHITECTURE.md` (§8, §9, §12, §14, §15), `.env.example`, `docker-compose.yml` (three pass-through variables), `scripts/demo.ts` (sign-in hint); server: `config.ts`, `index.ts`, `routes/index.ts`, `routes/alerts.ts`, `routes/rules.ts`, `routes/not-implemented.ts`, `db/alerts.ts` (parameter type), `ingest/router.ts`, `ingest/auth.ts`, and the tests listed in S6-15 plus `config`, `migrations` and `ingest/router` tests; web: `api/client.ts`, `app/routes.tsx`, `app/Layout.tsx`, `app/lazy-pages.ts`, `main.tsx`, `mocks/handlers.ts`, `i18n/en.json`, `i18n/es.json`, `vite.config.ts`, `tsconfig.node.json`, `Dockerfile`, `nginx/default.conf.template`, `test/render.tsx`. The user asked for the upload, client, CSP and rate-limit changes explicitly; the rest is the wiring S6's build list implies.

## S6-17 — Audit rows are ordered by a sequence, not by time (2026-10-27, S6)

Supersedes the cursor part of S6-07. CI failed on a 2-vCPU runner: the lockout test read `login_failed ×4, lockout, login_failed`. The rows were inserted in order, but reads sorted by `(at, id)`; the fifth failure and its lockout usually share a millisecond, and `uuidv7({ msecs })` fills the bits after the timestamp at random, so ties sorted at random (reproduced 2 times in 40 runs with `taskset -c 0,1`). Migration `003_audit-log-sequence.sql` adds `seq bigint GENERATED ALWAYS AS IDENTITY` (with unique `(seq DESC)` and `(action, seq DESC)` indexes, replacing the two `at` indexes); `GET /api/audit` orders by `seq` and its cursor is base64url of the last `seq`. A new migration rather than an edit of `002`, so a database that already ran `002` from this branch upgrades cleanly. The failed sign-in and the lockout it triggers are now written in one transaction, failure first, so the lockout row never exists without its cause. `test/auth/audit.test.ts` writes 40 rows in the same millisecond and expects them back in order (it fails with the old query every time); the login tests passed 40 runs in a row on two CPUs.

## S6-18 — `TRUST_PROXY` refuses `true` (2026-10-27, S6)

Supersedes S0's parsing, which passed `true` through. With `trust proxy = true` Express takes the left-most `X-Forwarded-For` address as the client, which the client writes itself: it could dodge the rate limits and the sign-in lockout and put any IP in the audit log, and express-rate-limit reports it as `ERR_ERL_PERMISSIVE_TRUST_PROXY`. `TRUST_PROXY` now accepts `false` (or `0`), a hop count from 1 to 32, or a comma-separated list of IPv4/IPv6 addresses, CIDR subnets and proxy-addr's `loopback`, `linklocal`, `uniquelocal`; anything else, `true` included, stops start-up with a message naming the variable. Addresses are checked strictly (no `10.1` shorthand). `test/security/rate-limit.test.ts` checks that the allowed forms make express-rate-limit report nothing and that a trusted proxy's `X-Forwarded-For` decides the lockout key; the login tests use `loopback`, the realistic setting for a proxy on the same host.
