## S8-02 — Cookie names per request: `__Host-` and `Secure` unless plain-HTTP development on localhost (2026-10-27, S8)

Supersedes S6-03 ("cookies are always `Secure`"). WebKit (Safari) does not store `Secure` cookies from `http://localhost` (S7b-18), and a `__Host-` cookie must be `Secure`, so Safari could not sign in to `npm run dev` or the Docker stack on `:8080`. `cookieMode(req, isProduction)` in `packages/server/src/security/cookies.ts` decides per request:

- `__Host-centinela` and `__Host-centinela-csrf` with `Secure` when `NODE_ENV=production`, when the request arrived over TLS (`req.secure`, which follows `TRUST_PROXY`), when any `X-Forwarded-Proto` value says `https` (believed even from an untrusted client, because it can only make the cookies stricter), or when the host is not a loopback name;
- `centinela-local` and `centinela-local-csrf` without `Secure` (still `HttpOnly` for the session, `SameSite=Strict`, `Path=/`, same lifetime) only for a plain-HTTP request whose host (`req.hostname`) is `localhost`, an address in `127.0.0.0/8` or `::1`, outside production. The Host header is client-controlled, but on plain HTTP nothing protects the cookies anyway, and production never relaxes.

Each mode reads only its own names: the session guard and the CSRF check look up the names of the request's mode, so an unprefixed cookie (which any service on localhost, or a sibling subdomain elsewhere, could plant) never authenticates an HTTPS or production request. Sign-in clears the other mode's cookies that the browser sent (with their own attributes, so the browser accepts the deletion): Chromium keeps `Secure` cookies on `http://localhost`, so a browser that signed in before this change would otherwise hold two CSRF cookies. The dashboard's client reads `__Host-centinela-csrf` and falls back to `centinela-local-csrf`; with the other mode cleared at sign-in, only one exists. The shared constants are `LOCAL_SESSION_COOKIE` and `LOCAL_CSRF_COOKIE` in `packages/shared/src/auth.ts`. Unprefixed names were chosen over running the local stack on HTTPS because a self-signed certificate would add a warning and a setup step to the three-command quick start.

Tests: `packages/server/test/auth/cookies.test.ts` covers the loopback check, both modes and their attributes, `localhost`, `127.0.0.1` and `[::1]`, trusted and untrusted `X-Forwarded-Proto`, LAN and public host names, production over plain HTTP, each mode refusing the other's cookies, CSRF reading the mode's cookie, and sign-in clearing the other mode. The S6 tests now say which mode they use (the test helpers return the cookie names with each session); `packages/web/test/auth.test.tsx` checks that the client repeats either cookie. Checked by hand with demo data, signing in and then signing out through the dashboard (a CSRF-protected request), in WebKitGTK 2.52.6 (MiniBrowser through WebKitWebDriver, from the Ubuntu archive) and Chromium 153 (Playwright): plain HTTP on `npm run dev` (`:5173`) and on the Docker stack (`:8080`) gives the local cookies, and HTTPS through a test-only TLS proxy gives the `__Host-` cookies with `Secure`. With the previous code, WebKit returned to the sign-in page with no cookie and `GET /api/auth/me` answered `401`. A Chromium profile holding `__Host-` cookies from before the change signs in over plain HTTP, ends up with only the local cookies and signs out.

## S8-03 — The quick start: three commands, nothing racing PostgreSQL (2026-10-27, S8)

`npm ci`, `docker compose up -d --build --wait`, `npm run demo`. `--wait` makes Compose return only when every service is running and those with a health check are healthy: PostgreSQL (`pg_isready`) and the server, which starts after PostgreSQL is healthy and applies the migrations before listening. The server image checks its health every 30 s, so the Compose file sets a 5 s interval for it; otherwise `--wait` would sit for half a minute after start-up. `npm run demo` then connects to a ready database (it also applies migrations, a no-op by then). The developer and test instructions use `docker compose up -d --wait postgres` for the same reason. The server image copied only `content/sigma`, so the stack on `:8080` had no playbook for Centinela's own rules, including the demo's critical alert; it now copies `content/centinela` too (one line in `packages/server/Dockerfile`, which the quick start needs).

Run from a fresh clone of the pushed branch with the local PostgreSQL and the dev servers stopped (ports 5432, 3000 and 8080 free): `npm ci` 0 vulnerabilities; `docker compose up -d --build --wait` exit 0 in 34 s (images from the build cache, see S8-04), PostgreSQL and server healthy; `npm run demo` 200,280 events, 37 alerts, `detected 19/19 scenarios`, exit 0; then sign-in at `http://localhost:8080` as `admin` / `centinela-dev` in WebKit and Chromium. The README quotes the demo's output from that run.

## S8-04 — Docker in this sandbox: workarounds that stay out of the repository (2026-10-27, S8)

As in S4-13, the sandbox reaches registries and npm only through a TLS-intercepting proxy on the host's loopback, and Docker Hub rate-limited one image pull (`429`). To run the quick start unchanged, the session started `dockerd`, pulled `nginxinc/nginx-unprivileged:1.29-alpine` from Google's Docker Hub mirror and tagged it locally, replaced the local `node:22-bookworm-slim` tag with an image that trusts the proxy's CA, and built both images once with `docker build --network=host` and the proxy as a build argument (proxy arguments are not part of the build cache key). `docker compose up -d --build --wait` then reused that cache and ran as written. None of this is in the repository; on a normal machine the three commands need nothing else.
