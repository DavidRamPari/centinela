# Session S5 decisions

## S5-01 — Sysmon field view: event data unchanged, envelope added, everything else filtered (2026-10-26, S5)

`src/parsers/sysmon/` accepts one JSON object per line in the nested shape (`Event.System` / `Event.EventData`, as in `rules/sigma/regression/`) or the flat shape (every key is event data; `EventID`, `Computer`, `TimeCreated`, `ProviderName` and `Channel` are read from it too). The envelope is validated with zod (`EventID` as a number, a digit string or an XML `#text` node, 0–65,535). Event data keys become fields exactly as written: S2 matches field names case-sensitively, so `Image`, `CommandLine`, `ParentImage`, `OriginalFileName` are never renamed or re-cased. Only keys that look like Windows field names (`^[A-Za-z][A-Za-z0-9_]{0,127}$`) are kept, at most 256 per event: dotted shipper keys (`event.action`, `host.name`), `@timestamp` and `__proto__` stay out of the field view, so data can never overwrite the ECS-style keys the parser sets (zod's records already drop `__proto__`). The raw line keeps everything. Strings are made storable (NUL and lone surrogates replaced) and cut to 8,192 characters; objects and arrays become JSON text (a value nested too deeply to serialize again becomes an empty string instead of throwing). `EventID` and `Computer` are added as fields when the data does not carry them, so both shapes produce the same field view (tested). ECS-style keys are added next to the Sigma ones: `process.executable`, `process.name`, `process.pid`, `process.command_line`, `process.parent.*` for event 1, `destination.ip`/`port`/`domain`, `network.transport`, `network.direction` for event 3, `file.path`/`file.name` for event 11. A line longer than the parser limit (65,536 characters) is rejected as `line too long` rather than cut into invalid JSON.

## S5-02 — Time, host, user and addresses (2026-10-26, S5)

Event time is the event data's `UtcTime` (Sysmon's own `2026-10-21 14:36:05.123`, always UTC), then the envelope's `SystemTime` (nested) or `TimeCreated` (flat); a time without an offset is UTC whatever the ingest `tz`, because Sysmon never writes local time. No usable time rejects the line (`missing timestamp` / `invalid timestamp`). The host is `Computer`, else the ingest context's host. `User` (`ANDES\m.condori`) becomes `user: "m.condori"` plus `user.domain: "ANDES"` (ECS); the Sigma field `User` keeps the full value. S3's mocks put the full `DOMAIN\name` in `user`; the real API now differs there, which only changes what the dashboard shows. `srcIp`/`srcPort` are set only for network connections (event 3), from `SourceIp`/`SourcePort`, normalized like the other parsers (IPv4-mapped IPv6 to IPv4, RFC 5952); the remote end goes to `destination.ip`. Process and file events have no `srcIp`, so S2's dedup key falls back to `user.name` for them.

## S5-03 — Event types and logsources follow ARCHITECTURE §4 exactly (2026-10-26, S5)

Event 1 → `process_start` / `process`, 3 → `network_connection` / `network`, 11 → `file_create` / `file`, all with outcome `success` (the event records something that happened); any other ID → `other` / `other` / `unknown`. Logsources are the single entry of the §4 table (`{product: windows, category: process_creation | network_connection | file_event}`, `{product: windows}` for the rest), which is what S4's `db/logsources.ts` rebuilds when events are read back; a test checks the two agree. Sigma also defines `service: sysmon` for Sysmon-only rules, but no vendored rule uses it and adding it would desynchronize S4's rebuild, so it is left out. An event whose provider (`Event.System.Provider`) or flat `ProviderName`/`Channel` names something other than Sysmon keeps its data but becomes `other`, so another provider's event 1 is never routed to process-creation rules.

## S5-04 — Golden test through the real pipeline (2026-10-26, S5)

`test/parsers/sysmon-golden.test.ts` reads every regression file with S2's decoder for concatenated JSON (`detection/json-stream.ts`), writes each object as one JSON line and sends it through `createPipeline()` (sysmon parser, detector with every repository rule, in-memory sink) in its own `ingest` call, so the event stored by that call is the sample's event. A sample is detected when an alert of its rule links its event. Result: 272/276 events (98.6%) and 267/267 files with the matches their `info.yml` expects; the verdict for every sample is identical to S2's direct `Event.EventData` evaluation, and identical again when the samples are rewritten in the flat shape. The four misses are the context events S2-09 describes.

## S5-05 — Centinela's Windows rules (2026-10-26, S5)

`rules/centinela/windows/` holds two base rules for the event types SigmaHQ's vendored subset does not cover: `centinela-win-lolbin-network-connection` (`network_connection`: certutil, bitsadmin, mshta or regsvr32 initiating a connection to an address outside the private, loopback, link-local and unique-local ranges, using `cidr`) and `centinela-win-lolbin-file-drop` (`file_event`: the same binaries creating a file outside `CryptnetUrlCache`/`INetCache`). Both are `medium`, tagged T1105 (and T1218 for the connection), `author: DavidRamPari`, MIT. They use the Sigma Windows field names (`Image`, `Initiated`, `DestinationIp`, `TargetFilename`) rather than the ECS keys of the Linux rules, so they read like the SigmaHQ Windows rules next to them and stay portable. No correlation was added: `rules/correlation/` is not S5's folder and the scenarios do not need one.

## S5-09 — Known gap: NDJSON objects with a `message` key (2026-10-26, S5)

S1's NDJSON decoder (`src/ingest/body.ts`) turns an object with a string `message` into that message. Sysmon events have no such key, so loggen's files ingest unchanged over NDJSON (`test/e2e/windows-api.test.ts`), but a shipper that adds `message` (Winlogbeat does) would send only the rendered message text to the parser, which rejects it. Sending such events as `text/plain` (one JSON object per line) works. Changing the decoder is S1's code; a follow-up could pass whole objects through for `source=sysmon`.
