## S12-R01 — A database error during the restore was taken for a malformed checkpoint (2026-11-14, S12 review)

Fixed in `d623bee`. Severity: medium. `loadCheckpoint` restored the detector, read the waiting events back by id and restored the buffer inside one `try`, and its `catch` answered `saved state is malformed`. A query that failed once (a dropped connection) therefore ended the restore "successfully": the correlation windows were restored, the buffer was not, the summary said nothing was restored, and because a state was "ignored" the good checkpoint was overwritten at once with one that had no waiting events. Those events were stored before the position, so nothing read them again. Shown with a reader whose `byIds` fails once: before the fix the restore resolved with `ignored`, and the brute-force alert that needed two waiting events never fired.

The read now happens outside the `catch`: a database error fails the restore as a whole, the checkpoint stays, and the next call tries again. Only `Detector.restore` refusing its snapshot counts as malformed. That alone would have made a second problem worse: an id in the saved state that is not a UUID made PostgreSQL refuse the query (`invalid input syntax for type uuid`), which would now fail every restore and with it every ingest call. The PostgreSQL reader therefore skips ids that are not UUIDs; they name no event. Tests: `checkpoint.test.ts`, "a failure to read the waiting events back is not a malformed state"; `live-detection.test.ts`, "ignores ids that are not UUIDs" and "a saved state that names waiting events that are not event ids is restored without them".

## S12-R02 — A second restore attempt started on top of the first (2026-11-14, S12 review)

Fixed in `875e708`. Severity: low, it needs two faults. When the restore failed while it read the events stored after the checkpoint, what it had already replayed stayed in the buffer and the detector. A valid saved state hid this, because restoring it replaces both. When the saved state was not used (another version after an upgrade, or malformed), the next attempt put the same events in again: with four of six failed sign-ins replayed before the failure, nine failures in total were evaluated as thirteen and raised the brute-force alert. A failed attempt now empties the buffer and puts the detector back to the snapshot taken before the first attempt. What the failed attempt had already evaluated is evaluated again by the next one, which is the at-least-once guarantee of a crash; that includes an attempt whose last step, saving the new checkpoint, is the one that fails. Test: `checkpoint.test.ts`, "a restore that fails while it reads the events stored after the checkpoint leaves nothing behind", for both kinds of saved state.

## S12-R03 — A checkpoint call could start the restore before the rule flags were loaded (2026-11-14, S12 review)

Fixed in `36ba136`. Severity: low. `ingest` and `restore` await `prepare` (the rule catalog loading `rule_state`) before the restore; `checkpoint` did not. When the database is down at start both `rules.ready()` and `pipeline.restore()` fail, and the first call to reach the database afterwards can be the checkpoint timer, fifteen seconds later. Its restore then replayed the events stored after the last checkpoint with every rule enabled, so a rule the analyst had disabled raised alerts. The restore itself now awaits `prepare` before it reads anything. Test: `checkpoint.test.ts`, "a checkpoint call that comes before the first restore loads the rule flags before stored events are evaluated".

## S12-R04 — The idle release ran right after a slow call and evaluated what had just arrived (2026-11-14, S12 review)

Fixed in `5508098`. Severity: low; the run still said it was not exact. The idle timer is armed when a call ends. A call that takes longer than `REORDER_IDLE_MS` (a large upload, a slow insert) lets it fire in the middle; the release then waited in the queue behind that call and, when its turn came, evaluated everything, including the events the call had stored a moment before. An older batch from a slower machine arrived late in a run that should have been exact, which is the case the buffer exists for. The queued release now does nothing when a call has armed a new timer since, or when `stop()` was called: a clean stop saves the buffer as it is. ARCHITECTURE §6.2 rule 3 says so. Tests: `live-pipeline.test.ts`, "does not release when a call was still running as the idle time passed" and "stop() also cancels a release that was waiting for a running call".

## S12-R05 — Times in a saved state were not checked to be times (2026-11-14, S12 review)

Fixed in `f6cd53b`. Severity: low; writing the checkpoint row needs access to the database. ARCHITECTURE §12 says the saved state is validated like any other input, but the schemas took any number as a time and any text as an event's timestamp. A waiting event saved with the time `1e300` was restored, and the next ingest call that released it failed with `RangeError: Invalid time value` inside the detector: the call answered 500 and the ten events released with it were never evaluated. A saved match whose event carries a timestamp that is not a date was restored too; when its window fired, the PostgreSQL sink failed with the same error, and the in-memory sink created an alert with that text as its first seen time. The buffer's schema now bounds times to the range of `Date`; the detector's schema does the same and requires timestamps to read as dates. Such a state is ignored as malformed. Tests: the tables of malformed states in `checkpoint.test.ts` and `detection/snapshot.test.ts`.

Not changed, and open:

- A time that is a valid date but lies ahead of the server's clock is restored as it is. Tried with a date far in the future in the saved state: a last released key in the future makes every later event late, and a watermark in the future evicts the restored windows at the first sweep. It needs the same access, or a server clock that ran ahead and was set back between two runs. Clamping saved times to the clock at restore would close it; whether a state from a clock that ran ahead is kept or dropped is a decision.
- An event id in a saved match is any text. One that is not a UUID is refused by the PostgreSQL sink when the window fires. The schemas do not ask for UUIDs because the detector and the pipeline do not, and their tests use other ids.

## S12-R06 — A line dated in year 0 failed the whole request (2026-11-14, S12 review)

Fixed in `1e717e6`. Severity: low. `0000-06-01T00:00:00Z` is a date for JavaScript, so the parsers and the orchestrator's check accepted it. PostgreSQL has no year 0 and refused the insert of the batch (`date/time field value out of range`): the request answered 500 and the valid lines of that batch were not stored. The condition existed before S12; it is fixed here because S12 added the check that is meant to keep timestamps the pipeline cannot use out of the store. Such a line is now rejected with `invalid timestamp`. NUL bytes and lone surrogates in a line were tried too and are stored without error. Tests: `live-pipeline.test.ts`, "rejects an event dated before year 1 instead of failing the call"; `live-detection.test.ts`, "a timestamp PostgreSQL cannot store".

## S12-R07 — One acceptance test passed without the code it names (2026-11-14, S12 review)

Fixed in `7834db1`, a test only. The acceptance tests were run against mutated copies of the code in a scratch clone: without the clamp to the receive time, without the future bound, without the replay after a checkpoint, without the waiting events in the snapshot, with a buffer that releases everything, with eviction counted from the newest match as in version 0.1, without the comparison of fingerprints, without the bound and without the late count. Each mutation failed the tests that name it, with one exception: "every group: an event dated minutes ahead does not evict the open windows" passes without the clamp. Sent with `ack=stored`, the event waits in the buffer and is evaluated last, so the buffer protects the windows and the clamp is never needed. The new variant sends the event with the default `ack=evaluated`, as an attacker would, and fails without the clamp. The eviction mutation also confirmed S12-07: with eviction counted as in version 0.1 only the late-host tests fail; the scenarios, the end-to-end test and the order tests do not change.

## S12-R08 — Open: a failed alert write loses alerts of events that were already acknowledged (2026-11-14, S12 review)

Severity: medium. When `AlertSink.upsert` rejects, the events of that step have left the buffer, the detector has counted them and the position is past them. Nothing evaluates them again, and the next checkpoint saves that state. Before S12 the request that failed carried those events and its sender retried it. With the buffer they can belong to another request. Observed with a sink that fails once: machine A sends an event that raises an alert with `ack=stored` and is answered 200 with `pending: 1`; machine B's request twenty seconds later releases A's event, the write fails and B is answered with the error; B's own event was stored, so its retry stores it a second time; after the sink recovers, a drain and a checkpoint, no alert exists for A's event. The idle release has the same loss and reports it through `onBackgroundError`. A real trigger does not need an outage: the sink locks open alerts with `FOR UPDATE`, so a deadlock with a bulk triage ends one of the two transactions. That trigger is a reading of the code, not something this review reproduced.

It is open because every repair is a choice. Keeping the candidates and writing them with the next evaluation is small, but a candidate the database always refuses would then block every later alert, so it needs a bound and a place for what is dropped. Treating a failed evaluation like a crash (forget the state, restore the checkpoint, replay) reuses a tested path, but a failure that repeats would then fail every ingest call. Retrying the write once covers a deadlock or a dropped connection and nothing longer. Separately, a call with `ack=stored` could answer for what it stored and report an evaluation failure in the log instead of telling its sender to send again. Until one is chosen the gap is listed in `docs/DETECTION.md`.

## S12-R09 — Open: the position assumes that ids only grow (2026-11-14, S12 review)

Severity: low. The checkpoint's position is the greatest event id handed to the buffer, and after a crash the server reads the events with a greater id. Ids are UUIDv7. Within one process they only grow, also when the clock steps back, because the `uuid` package keeps its last timestamp. Across a restart that memory is gone: if the server's clock was set back by more than the time the restart took, new events get ids before the position until the clock catches up. A clean stop is not affected, since waiting events are saved by id. After a crash those events are not read back. Observed with ids that restart lower in the second run: three failed sign-ins and a clean stop, four more and a kill, three more after the restart; `replayed` is 0 and the alert for ten failures does not fire, while with growing ids it is 4 and it fires. Options: generate ids that never go below the position (a floor on the timestamp part), or use a sequence column as the position. Both touch the id contract, so they are left to a session that owns it. Listed in `docs/DETECTION.md`.

## S12-R10 — Checked and left as it is (2026-11-14, S12 review)

- **The reorder buffer.** A property test written for the review, next to the one the suite already has: eight seeds, random batches with ties, random releases and snapshot round trips. Every event leaves exactly once, events that leave in order have strictly growing keys, an event is late exactly when it is behind the last released key, the size never exceeds the bound, and nothing leaves before the horizon unless the bound forced it.
- **The stream bound.** Through the pipeline the bound is exact under concurrent requests: with 999 streams and six requests for new hosts at once, one is stored and five are refused. The registry itself counts and then inserts, so six concurrent calls to `resolve` made 1,001 rows. Nothing calls it outside the pipeline's queue today; a second process that writes `token` streams would need a lock. Until S11 passes the token id, all tokens share one bound, as S12-04 says, so one token can use it up for the others.
- **SQL and the host.** Every statement added by S12 is parameterized; the host reaches the registry as a parameter and is limited by the query schema to 255 letters, digits, dots, underscores and hyphens.
- **Events read back.** The 9,338 events of the small demo, from its three sources (Linux auth, nginx access and Sysmon), were stored through the real pipeline and read back with the recovery reader: every one is equal to what the parser produced, logsources included.
- **The server wiring**, which has no automated test: run by hand against PostgreSQL after the fixes. A first start marks its place; `SIGTERM` logs `detector state saved` and exits 0; the next start logs `restored: true, buffered: 2` and the alert fires with all ten events; after `kill -9` the next start logs `replayed: 9`, the repeated firing folds into the alert it raised before (`count` 2, ten events) and no alert is doubled. The bearer token is redacted in the request log.
- **Gates.** `npm run demo` on two CPUs detects 19 of 19 scenarios and creates 37 alerts; the regression samples match 272 of 276 events; `npm run rules:lint` reports nothing new.
- **`ack=evaluated` from a token holder.** One request with an event dated now releases everything that waits, so a sender that keeps doing it turns live detection into evaluation on arrival, with every other machine's events counted as late. It cannot silence or evict a window: late events are still evaluated and S12-07 keeps their groups. S12-03 describes it for honest senders; as an attack it degrades ordering and nothing else.
- **Four lines in `checkpoint.test.ts`** assign `pipeline.components.eventReader` after the pipeline was built. The orchestrator reads its components once, when it is created, so the assignment does nothing. The tests still prove what they say, because the first run of each never restores; the lines were left as they are.
- **The cost of a large state.** 100,000 open groups in each of two rules: 62.6 MB of JSON, 2.0 MB compressed, 0.4 s to build the snapshot, 0.8 s to save and 2.3 s to load and restore, with the checks of S12-R05 in place. That agrees with what S12-05 measured.
- **A restore that keeps failing fails every ingest call**, by design: `ingest` waits for it. After R01 and R05 an id among the waiting events that is not a UUID, or a time that is not a time, no longer causes that. Two things still would: a saved match with an event id that is not a UUID, if the events replayed after it make its window fire (S12-R05), and an event row that fails validation when it is read back. Neither could be produced through the ingest endpoint in this review.

Not checked: memory at the bounds (100,000 waiting events of the largest size, a snapshot near the 512 MB limit); a state too large to serialize, where the code says the position stops advancing, so a crash would then replay everything stored since the last checkpoint that was saved, more than the 15 seconds `docs/DETECTION.md` states; a real database outage, as opposed to injected failures; a real shipper sending with `ack=stored`; GitHub's runner, where David runs CI by hand.
