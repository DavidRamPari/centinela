# Detection

How Centinela turns a normalized event into an alert: rule loading, the Sigma engine, correlation, alerts, performance, and how detection quality is measured. The contract (types, semantics, rule tables) is in [ARCHITECTURE.md](ARCHITECTURE.md) §5 to §7; the reasoning behind each choice is in [decisions/S2.md](decisions/S2.md) (engine), [decisions/S4.md](decisions/S4.md) (alerts in PostgreSQL) and [decisions/S5.md](decisions/S5.md) (Windows). The code is in [`packages/server/src/detection/`](../packages/server/src/detection).

## The path of an event

1. A parser turns a log line into a `NormalizedEvent`: normalized columns (time, host, user, source IP, action, outcome), a `fields` map that rules read (Sigma field names such as `CommandLine` or `cs-uri-query`, and ECS-style keys such as `source.ip`), and the `logsources` it belongs to.
2. The pipeline sorts each batch by event time, stores the events, then hands them to the detector.
3. **Routing** picks the Sigma rules whose `logsource` matches the event.
4. The **prefilter** drops the routed rules that cannot match (below), and the remaining rules are evaluated.
5. Every match feeds the **correlation engine**, which keeps per-group windows on event time.
6. Matches and correlation firings become **alert candidates**; the PostgreSQL alert sink deduplicates them into alerts and the live stream (`/api/stream`) tells open dashboards.

The detector never reads the wall clock: the same events give the same alerts in the same order ([`scenarios.test.ts`](../packages/server/test/detection/scenarios.test.ts), "the same sample gives the same alerts in the same order").

Every one of the 1,245 rules loads and compiles ([rules-report.md](rules-report.md), regenerated by `npm run rules:report`). Rules load from the repository's `rules/` folder only: one YAML document per file, duplicate keys refused, files above 1 MB refused, symbolic links not followed. SigmaHQ rules carry their author, a link to the rule at the vendored commit and the DRL 1.1 license into every alert they produce.

## The Sigma engine

### Routing

A rule applies to an event when, for one of the event's `logsources`, every key the rule's `logsource` sets (`product`, `service`, `category`) is equal, case-insensitively. An index built at load time maps each logsource to its rules, so a web request is never tested against Windows rules. A Windows process-creation event is routed to the 1,193 vendored process-creation rules, which is why the Windows benchmark is the slow one.

### Values

- Strings compare case-insensitively. `*` matches any run of characters and `?` one; `\*`, `\?` and `\\` are literal; a backslash before anything else is a literal backslash, so Windows paths need no escaping (pySigma's `SigmaString`).
- No regular expression is ever built from a rule value: wildcard patterns compile to equality, `startsWith`, `endsWith`, `includes` or a segment matcher that is linear per segment.
- Field names match exactly (case-sensitive), as in the Elastic and Splunk backends. A missing field never matches a non-null value; `null` matches a missing, null or empty field.
- Keyword lists (values without a field) are case-insensitive substring searches of the raw `message`.
- Every field value is cut to 8,192 characters before matching.

### Modifiers

| Modifier | Notes |
| --- | --- |
| `contains`, `startswith`, `endswith` | wrap the value in wildcards |
| `all` | every value of the list must match |
| `cased` | case-sensitive comparison |
| `windash` | each option dash may be `-`, `/`, `–`, `—` or `―`, positions independently. Implemented as a character class rather than pySigma's expansion into every combination (5^k strings for k dashes); it accepts exactly the same strings |
| `re` with `i`, `m`, `s` | RE2 semantics through `re2-wasm` (linear time). Patterns RE2 cannot express (backreferences, lookaround) make the rule unsupported (`regex:not-re2`); none of the vendored rules needs that |
| `base64`, `base64offset` | pySigma's offset algorithm. **Deviation:** encoded values match case-sensitively, because base64 is case-significant; SigmaHQ rules list each case variant of the plain text themselves |
| `wide` / `utf16le`, `utf16be`, `utf16` | encode before `base64` or `base64offset` |
| `cidr` | IPv4 and IPv6 networks; IPv4-mapped IPv6 addresses compare as IPv4 |
| `exists` | field present and not null (or the opposite) |
| `lt`, `lte`, `gt`, `gte` | numeric comparison; non-numeric values never match |
| `fieldref` | the field equals another field of the same event |

Modifiers apply left to right; incompatible chains (a string transform after `re`, `cased` on a number) make the rule unsupported (`modifier:incompatible`).

### Conditions

The full condition grammar: `and`, `or`, `not` with precedence `not` > `and` > `or`, parentheses, `1 of` / `any of` / `all of` with wildcard patterns and `them` (identifiers starting with `_` excluded), and a list of conditions meaning their OR. It is a recursive-descent parser in [`sigma/condition.ts`](../packages/server/src/detection/sigma/condition.ts).

### Not supported

A rule that uses one of these is listed as unsupported with the reason code shown, never silently half-evaluated. No vendored or Centinela rule uses any of them today.

| Feature | Reason code |
| --- | --- |
| `expand` (placeholders) and any modifier not in the table above | `modifier:expand`, `modifier:unknown` |
| Aggregations in a condition (`\| count() by …`) | `condition:aggregation` |
| `near` | `condition:near` |
| `timeframe` in a single-event rule | `detection:timeframe` |
| Multi-document YAML (rule collections) | `yaml:multi-document` |
| Regular expressions RE2 cannot compile | `regex:not-re2` |
| Correlation conditions `lt`, `lte`, `eq` (absence-style rules), `temporal` with a condition, correlation `aliases` | `correlation:condition`, `correlation:aliases` |

## Correlation

Centinela implements a subset of the Sigma correlation specification ([ARCHITECTURE.md](ARCHITECTURE.md) §6):

- **Types:** `event_count` (matches in the window), `value_count` (distinct values of `condition.field`), `temporal` (every referenced rule matched, any order) and `temporal_ordered` (in the listed order).
- **Windows** run on event time: `timespan` (or `timeframe`) is a sliding window `[t − timespan, t]` per group, conditions (`gt`, `gte`, combined with AND) are evaluated on every new match, and when a correlation fires it emits one candidate with its contributing events (the latest 100) and clears that group's window.
- **Groups** are the `group-by` values from the event's fields; an event missing one does not take part.
- **Chaining:** a correlation may reference another correlation. The inner firing counts as one match of the outer rule, at the time of its last event and with its group's values. Correlations are evaluated in dependency order; unknown references and cycles make a correlation unsupported. `centinela-ssh-bruteforce-success` chains on `centinela-ssh-bruteforce`, so a member of staff who mistypes a password twice and then signs in never fires it.
- **`generate: false`** silences only the Sigma rules a correlation references (building blocks, such as the single failed SSH sign-in), not referenced correlations: the brute-force alert still appears next to the "brute force then success" alert (decision D-010; pySigma silences both).
- **Late events:** events up to 60 seconds older than a group's newest event are accepted; older ones are stored but ignored by correlation. Group state is evicted once the newest event time seen passes its newest entry plus the timespan.
- **Bounded state:** at most 1,000 matches per group and 100,000 groups per correlation (oldest dropped first), and `value_count` keeps one entry per distinct value, because IP addresses and user names in logs are attacker-chosen.

Centinela's correlation rules:

| Rule | Type | Fires when | Level |
| --- | --- | --- | --- |
| `centinela-ssh-bruteforce` | `event_count` | 10 or more failed SSH sign-ins from one IP to one host within 5 minutes | high |
| `centinela-ssh-password-spraying` | `value_count` | 10 or more distinct user names failing from one IP within 10 minutes | high |
| `centinela-ssh-bruteforce-success` | `temporal_ordered` | a brute force from an IP, then a successful sign-in from that IP within 30 minutes | critical |
| `centinela-privileged-account-created` | `temporal_ordered` | a new account, then that account added to `sudo`, `wheel`, `adm` or `root` within 10 minutes | high |
| `centinela-web-scanning-burst` | `event_count` | 50 or more 404 answers to one IP on one host within 2 minutes | medium |

## Alerts

- **Deduplication key:** rule and group key for correlations; rule, host and the first present of source IP, user or image for single-event rules.
- **Suppression:** a match whose key has an open (`new` or `acknowledged`) alert seen in the last 15 minutes folds into it: the count grows, `lastSeen` moves, events are linked (at most 100) and entities merged (at most 100 each). Otherwise a new alert starts. The PostgreSQL sink does this in one transaction under one advisory lock, so the server and `npm run ingest` or `npm run demo` can write to the same database ([decisions/S4.md](decisions/S4.md), S4-01).
- **Triage:** `new` → `acknowledged` → `closed` (a resolution is required), and `closed` → `new` to reopen; every change is audited and published on the live stream.
- Each alert carries its rule's ATT&CK techniques; tactics come from the ATT&CK data in `data/mitre-attack/`, not from the rule's tactic tags.

## Performance

A Windows process-creation event is routed to 1,193 rules. Evaluating each one costs about 1 ms per event, about 900 events per second (measured in S2 before the measures below). Three measures, all in `packages/server/src/detection/`:

1. **Shared predicates.** Identical selections and detection items across rules compile once and are evaluated at most once per event.
2. **A literal index.** Every case-insensitive literal pattern (`v`, `v*`, `*v`, `*v*`) of each field goes into one index per rule set: a map, a trie, a reversed trie and an Aho–Corasick automaton ([`sigma/literal-index.ts`](../packages/server/src/detection/sigma/literal-index.ts)). Each field value is scanned once per event.
3. **The prefilter.** Each rule gets a set of literals of which at least one must match for it to be true, derived from its condition: AND keeps its smallest child set, OR takes the union, NOT and non-literal items give none ([`prefilter.ts`](../packages/server/src/detection/prefilter.ts)). Only rules whose requirement matched are evaluated, plus the 29 rules with no requirement (24 Windows process-creation rules and 5 Linux built-in rules). The prefilter only skips rules that cannot match: the tests compare its results with exhaustive evaluation on both benchmark mixes, and every modifier test runs with and without the cache.

### Benchmark

`npm run bench` replays two deterministic mixes through the engine on one thread, after a 5,000-event warm-up, without rule loading or event construction in the timing ([`bench.ts`](../packages/server/src/detection/bench.ts)):

- **Linux/web mix:** real auth.log and nginx lines through the parsers, mostly routine traffic plus brute force, scanning and SQL injection.
- **Windows mix:** Sysmon process creation, nine routine processes for each SigmaHQ regression sample.

Run on 2026-10-27 (session S8), on the cloud VM the build sessions use: 4 vCPUs (Intel Xeon @ 2.10 GHz), 15 GiB of memory, Node.js 22.22.0:

```text
npm run bench: 1240 Sigma rules and 5 correlation rules compiled in 1.11 s (node v22.22.0)
linux/web mix                100,000 events in 1.17 s = 85,255 events/s (20,658 alert candidates)
windows process_creation mix 100,000 events in 16.79 s = 5,956 events/s (19,334 alert candidates)
```

The full pipeline is slower than the engine: `npm run demo` stores every event and alert in PostgreSQL in batches of 1,000, and ingested its 200,280 lines at 5,535, 5,847 and 6,727 events per second in three runs on the same VM (database on the same machine, natively or in Docker). Demo ingestion is bound by the database writes, not by detection.

## How detection quality is measured

### Ground truth from the demo generator

`packages/loggen` generates three days of logs for the fictional company "Andes Retail" (seed 42): four Linux hosts and two Windows workstations, about 200,000 lines in all, and 19 attack scenarios. Each scenario is labeled in `ground-truth.json` with its ATT&CK techniques, hosts, time range, entities (IP addresses, user names) and the rules expected to fire; the table is in [ARCHITECTURE.md](ARCHITECTURE.md) §4.3. Every SigmaHQ scenario was written against the rule it targets, and every Windows command line is inert (documentation addresses, a harmless encoded command, no real tool).

A scenario counts as detected when **each** of its expected rules raised an alert whose time range overlaps the scenario's and that shares an IP address or user name with it ([`ground-truth.ts`](../packages/server/src/db/ground-truth.ts)). Other alerts for the same scenario are allowed.

| Check | Where | Result |
| --- | --- | --- |
| Every scenario detected, small and full 3-day sample, in memory | [`scenarios.test.ts`](../packages/server/test/detection/scenarios.test.ts) | 19/19 |
| Every scenario detected through PostgreSQL | [`e2e/detection.test.ts`](../packages/server/test/e2e/detection.test.ts) | `detected 19/19 scenarios` |
| Background traffic raises no `high` or `critical` alert (Linux, web and Windows hosts) | the same two tests | `0 high/critical alerts from background traffic` |
| Workstation background raises no alert at any level | [`windows.test.ts`](../packages/server/test/detection/windows.test.ts) | no alert |
| The demo data set, end to end | `npm run demo` | `detected 19/19 scenarios`; 37 alerts (1 critical, 17 high, 16 medium, 3 low) |

### SigmaHQ regression samples

SigmaHQ ships recorded Windows events that each rule must match. Every event in `rules/sigma/regression/windows/process_creation/**` is evaluated against its rule, directly (S2's golden test) and through the Sysmon parser and the whole pipeline (S5's golden test): **272 of 276 events match and 267 of 267 files pass** ([rules-report.md](rules-report.md)). The four events that do not match are context events in two `findstr` samples (the parent `cmd.exe` and a piped process) whose `info.yml` expects one match per file.

### Content-pack fixtures

Every playbook in the content pack comes with positive and negative test events written by the generator. `npm run content:validate` runs each one through the engine (positives must match, negatives must not), and `npm test` holds the result as a regression baseline:

- SigmaHQ rules: **4,850 of 4,851 fixtures pass (99.9%)** for 1,221 rules ([content-pack-report.md](content-pack-report.md)). The 8 fixtures that failed in S7 were not engine bugs ([decisions/S7.md](decisions/S7.md), S7-08). On 2026-10-30 they were rewritten with the `repair` command of `tools/content-pack`, which sends the engine's error back to the model; 7 of them pass now. The last one cannot pass: the vendored rule *COM Object Execution via Xwizard.EXE* requires a `CommandLine` that equals `RunWizard` and also contains a GUID, which no event can satisfy. This project reported it and SigmaHQ merged the fix, `CommandLine|contains` ([SigmaHQ/sigma#6546](https://github.com/SigmaHQ/sigma/pull/6546)); the fixture will pass once `rules/sigma` is updated to a later SigmaHQ commit. The bug led to the [rule lint](#rule-lint).
- Centinela's rules: **36 of 36 fixtures pass** for the 9 detection rules; the 5 correlations have a playbook only ([content/centinela-report.md](../content/centinela-report.md)).

### Rule lint

A rule can be valid Sigma and still never match: an exact `Image` value that is not a full path, a `startswith` that no path begins with, a folder where a file path is expected. Nothing fails; the rule, or one of its filters, is silently dead. `npm run rules:lint` ([`lint.ts`](../packages/server/src/detection/lint.ts)) finds these conditions without running the rule. It reads values with Sigma's escaping (`\\`, `\*` and `\?` are escapes) and skips items with a modifier the engine does not support. Each check comes from a class of bugs that SigmaHQ fixed in October and November 2026:

| Check | Why the value never matches | Example (the SigmaHQ pull request that fixed it) |
| --- | --- | --- |
| `partial-path` | `Image`, `ParentImage`, `ImageLoaded`, `TargetFilename`, `SourceImage` and `TargetImage` hold full paths, so an exact value must be one (or a name such as `System` that Windows logs for processes without a file) | `Image: '\AgentExecutor.exe'` ([#6567](https://github.com/SigmaHQ/sigma/pull/6567)), `TargetFilename: 'host_ip.ps1'` ([#6518](https://github.com/SigmaHQ/sigma/pull/6518)) |
| `folder` | a file path never ends with a separator, so neither can an exact or `endswith` value | `Image\|endswith: '\AppData\Local\Apps\2.0\'` ([#6554](https://github.com/SigmaHQ/sigma/pull/6554)), `TargetFilename\|endswith: '\Windows\System32\winevt\Logs\'` ([#6453](https://github.com/SigmaHQ/sigma/pull/6453)) |
| `bad-start` | a `startswith` value must be able to begin a full path | `Image\|startswith: ':\Program Files'` ([#6565](https://github.com/SigmaHQ/sigma/pull/6565)), `TargetFilename\|startswith: '\Logging\CmdletInfra\LocalPowerShell\Cmdlet\'` ([#6454](https://github.com/SigmaHQ/sigma/pull/6454)) |
| `separator` | Windows paths use `\`, Linux and macOS paths use `/` (by `logsource.product`) | `Image\|endswith: '/xwizard.exe'` in a Windows rule ([#6562](https://github.com/SigmaHQ/sigma/pull/6562)), `Image\|endswith: '\node'` in a Linux rule ([#6483](https://github.com/SigmaHQ/sigma/pull/6483)) |
| `file-name` | `OriginalFileName` is the bare file name from the executable's version information | `OriginalFileName: '\msiexec.exe'` ([#6549](https://github.com/SigmaHQ/sigma/pull/6549)), `OriginalFileName: '\nslookup.exe'` ([#6455](https://github.com/SigmaHQ/sigma/pull/6455)) |
| `cmd-space` | an exact command line does not begin or end with a space | `CommandLine: ' -dhl'` ([#6567](https://github.com/SigmaHQ/sigma/pull/6567)) |
| `dword` | Sysmon logs registry numbers in hexadecimal: `DWORD (0x00000001)` | `Details: 'DWORD (00000001)'` ([#6560](https://github.com/SigmaHQ/sigma/pull/6560)) |
| `unsatisfiable` | no exact value of the key also satisfies the other conditions on the same field in the same selection; the engine's own matchers decide | `CommandLine: 'RunWizard'` next to a `CommandLine\|re` that requires a GUID ([#6546](https://github.com/SigmaHQ/sigma/pull/6546)) |

Run on each rule as it was before its fix, the lint flags 28 of the 29 files that these twelve pull requests changed; the 29th had a misspelled registry key (`CurentControlSet`), which no shape check can see. Run on the fixed versions it finds nothing, except one condition: `Image|endswith: '/xwizard.exe'`, which slipped into the final version of #6546 and was fixed two days later in #6562.

[#6546](https://github.com/SigmaHQ/sigma/pull/6546) and [#6567](https://github.com/SigmaHQ/sigma/pull/6567), six rules in all, came from this project, and the checks are proposed as a validator for SigmaHQ's own CI in [SigmaHQ/pySigma-validators-sigmaHQ#86](https://github.com/SigmaHQ/pySigma-validators-sigmaHQ/issues/86). A lint that a maintainer is asked to run must not cry wolf, so it was tried on every folder of SigmaHQ's master branch (commit `53b90df6`, 2026-11-06). Every finding there is a condition that cannot match in the logs the rule is written for:

| SigmaHQ folder | Rules | Findings |
| --- | ---: | --- |
| `rules` | 3,164 | 4 values in 3 rules: an Avira filter with exact folder paths, `OriginalFileName: '\REGSVR32.EXE'`, and a filter on `/usr/share/icons/` in a Windows rule |
| `rules-emerging-threats` | 474 | 1: `ParentImage\|endswith: '\bash'` in a Linux rule, which makes the rule match nothing |
| `rules-threat-hunting`, `rules-compliance`, `rules-placeholder` | 169 | none |
| `deprecated`, `unsupported` | 265 | 14, in rules that SigmaHQ no longer maintains |

In Centinela's vendored rules (SigmaHQ commit `05d1031f`, 2026-10-21) the lint reports 22 findings in 14 rules. [`rules/lint-baseline.json`](../rules/lint-baseline.json) lists each one with where it stands upstream: 13 of the rules are fixed in SigmaHQ after that commit (#6546, #6549, #6565 and #6567), and `proc_creation_win_regsvr32_remote_share.yml` is not fixed yet. `npm run rules:lint` exits with 1 on a finding that the baseline does not list, on a baseline entry that no longer matches and on a file it cannot read, and `npm test` holds the same comparison, so updating `rules/sigma` to a newer SigmaHQ commit shows which entries to remove. Any folder of Sigma rules can be checked, such as a SigmaHQ checkout next to this repository:

```bash

```

## Known gaps

- The Sigma features in "Not supported" above, in particular range and absence conditions in correlations.
- Correlation state lives in one process (decision D-003): several server processes would not share windows.
- Field names are case-sensitive; a shipper that renames `CommandLine` to `commandline` defeats the Windows rules.
- `POST /api/ingest` with NDJSON turns an object with a string `message` key into that message, so Sysmon events from a shipper that adds `message` (Winlogbeat does) are rejected; send them as `text/plain`, one JSON object per line ([decisions/S5.md](decisions/S5.md), S5-09).
